# Shipped hooks — full per-hook reference

Moved verbatim out of `README.md` (which keeps the overview and the fixed menu list): these
per-hook descriptions are the complete behaviour contract for each shipped hook and grew far
past what a front page can carry.

**One client fact decides the shape of every Stop-time advisory in this set.** On Claude Code a Stop
hook's `hookSpecificOutput.additionalContext` is not a passive note: the client re-invokes the model
with it (observed in Claude Code 2.1.260, 2026-09-07 - a `hook_additional_context` transcript entry
followed by a fresh assistant turn seconds later, with no user input between them). A Stop advisory
emitted that way is a soft block, and an advisory repeated on every Stop re-invokes the agent on
every Stop: it answers, stops, is re-invoked, answers again, until the user interrupts.

So no hook in this set emits `additionalContext` on `Stop`/`SubagentStop` any more. The shared
adapter (`Write-HookResult`) emits **`systemMessage`** there, which the client shows to the user
without starting another model turn; every other event keeps its documented shape, and a genuine
refusal is still `decision:block`. The bound stays as well - once per session per unchanged state -
because a repeated message is noise even when it costs no turn. Requirements that concern the
*closing reply* (`MCP used:`, `Skills used:`, the session summary) are delivered **before** the task
instead, at SessionStart and on the prompt, so the reply that ends the task carries them with no
extra turn. Once a task has published its DONE / REMAINING wrap-up, `Mcp-Usage-Check`, `Skills-Check`
and `Rules-Check` judge a later correction turn of that same task together with the published
wrap-up, so a gate that blocks afterwards never makes the agent repeat those lines; a new task never
inherits them.


**Concise-message standard.** Authored hook text states the observed condition, affected identity/scope and exact clearing action once; use precise task-triggered policy pointers for detail. Preserve commands, dynamic findings, safety constraints and UNKNOWN/error distinctions. Never truncate facts, encode prose or claim tokenizer savings from character counts. Existing ContextHooks checks bound all hook packages' literal text plus representative output semantics; a new message or budget increase requires the same semantic review. Raw user memory and configured review instructions remain verbatim.

**Procedural defaults.** All nonsafety findings are advisory once per fingerprint; only confirmed secrets, unsafe deletion/data loss, and verified live/leaked test processes block. Persisted user overrides win; undetermined state is silent.

**Hook deadline.** Hooks that adopt the shared `_budgetlib.ps1` (Dependency-Version-Check first;
Ci-Status-Check folds its GitHub budget into it) derive a deadline from the timeout the installer
registered - `timeoutSeconds` in the runtime's `.hookmaker-runtime.json`, 5 s of margin, 60 s when
nothing is recorded - and bound every child process by the time left, so the client never kills
them mid-child and leaves the user with no answer at all. Ci-Status-Check loads its private
sibling budget before shared initialization; the shared process runner clamps Git discovery as well
as GitHub calls to that deadline. An expired deadline starts no new child and returns timeout/unknown,
never successful CI evidence. Process cleanup retains the existing 5-second reserved margin.

All advisory hooks are token-efficient by design: they stay **silent** unless a deterministic
signal fires (staleness, wrangler config, out-of-sync git, pending Dependabot PR, unverified
push), they respect a per-project **cooldown/fingerprint**, they never loop (`stop_hook_active`
guard), and the decision always stays with the AI — every reminder explicitly allows finishing
without action. The GitHub hooks degrade safely (silent, never a false "all clear") when git,
a remote, `gh`, authentication, or network access is missing.

Stop **gates** stand down on their own re-entry, never on anyone else's. `stop_hook_active` is set for *any* gate's block, so a hook that exited on that flag alone went silent whenever an unrelated hook happened to block first on the same Stop. Each gate now writes and reads its own session-scoped marker (`Test-StopStandDown` / `Set-StopBlockMarker` in `hooks/_hooklib.ps1`): one hook's block never mutes the others, and no gate repeats its own. Advisory hooks keep the plain `stop_hook_active` guard — their message has already gone out, and repeating it on every continuation Stop would be noise.

Terminating an owned process tree is bounded, identity-checked, and reports what it did. `hooks/_processtree.ps1` owns it, and every hook gets it through `_hooklib.ps1`. It used to recurse once per level, issuing a fresh process query at each one, with no depth limit, no total deadline, no ownership check and no return value — so a caller that had just spent its whole budget handed control to something that could spend an unbounded amount more, and then could not tell whether it had worked. Now one bounded query takes a single snapshot and the tree is walked in memory, which is what makes a total deadline achievable at all; a process that started **before** its recorded parent is a recycled process id rather than a descendant and is left alone; the walk is capped in depth and breadth and never visits a process twice, so a cycle in the parent map terminates instead of looping; a request to clean up the cleaner's own tree returns before it enumerates anything, so the caller's whole tree is protected and not merely its own process id; and survivors are confirmed by looking rather than assumed from having asked. The verdict distinguishes a tree confirmed gone from cleanup that is unproven, and names what survived — issuing a termination request was never evidence of absence. When the process query itself is unavailable, cleanup falls back to the one process it can identify directly and reports partial coverage; it never falls back to matching by process name, which cannot tell an owned process from a stranger.

Matching lifecycle hooks for the same event run concurrently and are intentionally independent;
their registration order (and menu position) is display-only and never guarantees execution order.
`Cloudflare-Deploy` and `Test-Temp-Cleanup` hand off state through a small fingerprinted file
instead of assuming one runs "after" the other on the same Stop. The native pre-push chain is the
only ordered sequence.
It honors Git's resolved `core.hooksPath` (default, relative, nested, absolute, and paths with spaces), preserves an existing pre-push hook once, and is idempotent.



## Finding severity (035)

| Condition | Default role / result | Repetition |
|---|---|---|
| Confirmed staged/tracked secret | Gate, block | Once per session/event/fingerprint |
| Unsafe unowned deletion or data loss | Gate, block | Once per session/event/fingerprint |
| Verified live or leaked test process | Gate, block | Once per session/event/fingerprint |
| CI pending/unproven/failed, workload review, skills/rules/MCP/docs/graph/memory, UTF-8 style, Git synchronization, historical test evidence | Advisory, exit 0 | Once per session/event/fingerprint |
| State cannot be determined | Silent, exit 0 | No finding or success invented |

Persisted `block` and `off` enforcement choices remain authoritative (`HOOK_ENFORCEMENT`, or the hook-specific Skills/MCP/Rules enforcement key) and govern FINDINGS only: `off` silences the closing half, while the pre-task `context` advisory that opens the session still runs. Advisories never emit a blocking decision or grant tool permissions. Stop messages use passive `systemMessage`; both Claude Code and Codex keep their event adapters. Dynamic facts/paths/commands are retained, not truncated. The roughly 50% hook-message reduction is bounded by **66,157 authored guidance characters**, at most half of the **28be7d1 baseline (289 groups / 132,315 characters)**, with per-package half ceilings in `scripts/_testhookguidance.ps1`.

The shipped set remains 30 packages. No hook/client/event/menu number/installer path was removed; existing self-contained runtime payloads still carry their required companions. The shared `_hooklib.ps1` is a documented pre-existing oversized file and may not grow; new/other changed source stays at or below 800 lines. CI/test outcomes remain evidence, never seeded or converted into a pass by advisory delivery. The severity table governs every description below: evidence classifications such as UNKNOWN or partial never certify success and do not grant extra block authority. If state cannot be determined, the required behavior is silent exit 0. Native secret-scan safety remains unchanged.

## `Cross-Project-.ai-Knowledge-Sync`

**Runs:** pre-task (SessionStart, UserPromptSubmit).

The sync engine: stages changed `.ai` knowledge from related projects for review. Each review is an **owned generation**: the staging directory is proven to sit inside the configured destination through every internal ancestor (a junction on `inbox`, `.ai` or `.cross-project-sync` refuses the whole operation rather than redirecting it out of the project), the new generation is built and its copied bytes verified against the snapshot BEFORE the superseded one is retired, and the acknowledgement is bound to the generation on disk rather than to a matching fingerprint string.

A source that changes mid-review therefore queues a new generation instead of deleting the one being read; a package that is gone or tampered with is rebuilt instead of announced as a dead path; and staging that could not be retired is reported as **deferred cleanup**, which is a different outcome from a failed review.

## `Git-Sync-Check`

**Runs:** pre-task (SessionStart) + PreToolUse + post-task (Stop, SubagentStop).

Reports uncommitted/unpushed/unpulled work as nonblocking context; SessionStart also captures a sanitized worktree/local-branch baseline. Stop/SubagentStop remains a detector/advisory, not an executor: it never runs `git add`/`commit`/`pull`/`push`/`merge`/`rebase`/`branch -d`/`worktree remove`. It requests reconciliation only within the user's existing authorization. Failing tests, incomplete work, unrelated changes, protected files, conflicts or missing permission mean preserve the work and report the limitation, not force a Git operation.

A branch/worktree that existed unchanged before the task is advisory context only, never a blocker, and a branch that is pushed to its own upstream but not yet merged is not itself a blocker either (this hook never infers that every remote branch must be merged). A real git inspection runs on every Stop/SubagentStop (never a blind time-only skip; the worktree/branch scan is bounded and degrades honestly); Git synchronization, branch disposition and identity findings use passive `systemMessage` and exit 0 by default on both clients; pre-task output keeps its event-specific context shape. Only a persisted `block` override changes that default.

Repeat output is gated by a fingerprint of the actionable state (branch/HEAD/upstream/ahead-behind/status plus any task-scoped worktree/branch findings) combined with the session id, so a given state is reported once per session, while a changed state or a new session is evaluated and reported again immediately. Worktree records are separated by their headers. Dirty-state comparison includes index blob ids and file-content hashes, so edits to an already-dirty path are detected. The signature is limited to 500 paths, 16 MB and five seconds; incomplete reads and older signatures mean UNKNOWN.

Every SessionStart also reminds the agent that old and new commits must carry only the public address `Kiaro.Sama.Dev@gmail.com` (commits carrying another address for the user are rewritten); at Stop it counts non-public, non-bot identities in this session's commits (counts only, never an address) and lists merged and unmerged local and remote-tracking branches so every branch gets a disposition. PreToolUse (steering V38): a branch/worktree/PR-creating command (`git checkout -b`, `git switch -c`, `git branch <new>`, `git worktree add`, `gh pr create`) gets a reminder that work stays on the default branch unless the user asked or a forcing reason is stated (then ONE branch and ONE PR); a `git push` with uncommitted changes gets the push-once reminder (every push and PR starts its own CI run).

Context only - never a permission decision. At Stop the branch list is followed by the open pull requests. Existing installs move to the new event set through event migration v3. The remote is fetched at most once per `FETCH_MIN_INTERVAL_MINUTES` (default 5, `0` = every event) per repository; a push keeps the remote-tracking ref current on its own, and an offline fetch keeps its "last known remote state" note and retries on the next event.

## `Feature-Request-Check`

**Runs:** pre-task (UserPromptSubmit) + post-task (Stop, SubagentStop).

A detector/advisory for the **skill chain**, never a completion block. `UserPromptSubmit` is advisory: when a prompt reads as a feature request it says to run the mattpocock chain — `grilling` + `domain-modeling`, then Spec Kit in order — `speckit-specify`, `speckit-clarify`, `speckit-plan`, `speckit-tasks`, `speckit-analyze`, `speckit-implement`, with `tdd` at the agreed seams and `code-review` inside the last one — instead of coding straight from the prompt. Detection is deliberately conservative: an explicit phrase (`feature`, `feature request`, `as a user`, `should be able to`, `make it possible`, and the Persian equivalents) is decisive on its own, while a build verb (`add`/`implement`/`build`/`create`/`introduce`/`support`) counts only when it has an object within 60 characters **and** the prompt carries no bug vocabulary — so “fix the crash by adding a guard” stays a bug fix.

On `Stop`/`SubagentStop`, a complete transcript showing a feature request without both interview calls receives one passive `systemMessage` per prompt-set fingerprint. Missing or partial transcripts stay silent, not all-clear; its own guidance never counts as a user request. The reminder permits explaining why this was not a feature; it does not parse that explanation or record interview completion. No `decision:block` or continuation context is emitted.

`.env`: `MAX_TRANSCRIPT_BYTES` (default `20000000`; the transcript is read from the **start**, where the feature prompt and the grilling call both are, and values below `100000` are ignored). The Stop advisory checks BOTH openings of the chain: a transcript holding only `grilling`, or only `domain-modeling`, names the missing half and states the order (grilling + domain-modeling, then Spec Kit in order: specify, clarify, plan, tasks, analyze, implement). Everything else is unchanged - once per prompt-set fingerprint, silent without a transcript, advisory-only on Kiro.

Its advisory also carries the mid-task intake line: a new request inside a running task is recorded as a request delta and routed through Spec Kit before dependent edits; only work that depends on an open question waits.

## `Speckit-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit).

**Advisory and detector - it never blocks.** Spec Kit carries the spec-driven workflow and one `speckit-*` skill runs on every task that changes the project, so this hook names the route that matches what is actually on disk rather than repeating a generic reminder. It reads three fixed things under the project root and nothing else - `.specify/`, `.specify/memory/constitution.md`, and one non-recursive listing of `specs/` to find the feature whose `tasks.md` is newest - then counts that one file's unchecked items.

No `.specify/` yet gives `speckit-init` then `speckit-constitution`; infrastructure with no feature gives the full chain from `speckit-specify`; a feature with unchecked items is named with its exact open count and routed to `speckit-implement`; a finished feature routes resumed work to `speckit-converge`. **Unreadable is never reported as absent**: a `specs/` it cannot list, or a `tasks.md` it cannot read, is stated as UNKNOWN, because claiming “there is no plan here” on a failed read sends the agent to rebuild work that already exists.

It never executes a skill, a binary or `git`. `UserPromptSubmit` speaks only for a prompt that describes work changing the project, using a definition shared with `Feature-Request-Check` so the two can never disagree - and deliberately including bug and regression wording, which the feature classifier subtracts on purpose, because the 2026-09-19 rules route a bug through the workflow too. One message per session per project state and request, so initialising the project mid-session still gets the follow-up route.

`.env`: none. The active feature comes from `.specify/feature.json` when it names a spec-bearing folder, else folder recency (labelled as such). A new request mid-task gets the intake line (dated request delta, requirement IDs, acceptance criteria, amend the affected spec/plan/tasks); the message is keyed per request, and only work that depends on an open question waits. When `.specify/` exists and `.ai/COMMANDS.md` records no Spec Kit refresh or the last is 30+ days old, it adds the fixed monthly refresh text once per recorded date; it reads files only and never runs `specify`.

## `Ai-Memory-Load`

**Runs:** pre-task (SessionStart, UserPromptSubmit). **Menu label:** `Ai-Context-Load`.

Loads `.ai/memory.md` (the startup router) directly into context and lists every other top-level `.ai/*.md` file by name, so the agent can route to the relevant project context without loading unrelated files. Fingerprinted on the router content plus the file set; capped with a truncation note; silent when no `.ai/memory.md` exists.

## `Ai-Memory-Check`

**Runs:** post-task (Stop). **Menu label:** `Ai-Context-Check`.

If the project's `.ai` context is stale, asks the AI to update whichever existing `.ai/*.md` files are relevant — or finish if nothing durable was learned.

## `Graph-Read-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit).

If `graphify-out/graph.json` exists, the SessionStart note gives the compact graph-availability policy once; `UserPromptSubmit` reminds again **only when the prompt itself suggests codebase structure/dependency/call-path/architecture/broad-impact understanding is needed** — in **English or Persian** (معماری/ساختار/وابستگی/مسیر فراخوانی/ماژول/نقطه ورود/بازنویسی/کل کدبیس …) — fingerprinted per session + graph version so an unchanged reminder isn't repeated. When **no** graph exists but the task materially needs codebase-wide understanding, it advises creating one first (a bounded, non-executing `graphify` availability check, then create-then-query) or, if Graphify is unavailable, one bounded fall-back to targeted source inspection; it stays silent for docs/config/local edits.

Detector/advisory only — it never runs Graphify or project code.  **Runs alongside Codebase Memory:** every project carries both graphs, so a CBM index no longer silences this hook — `Cbm-Read-Check`/`Cbm-Update-Check` speak for code structure while this one keeps graphify's own ground (docs, specs, papers, images, video and whole-project query/path/explain views). `.env`: `CBM_CACHE_DIR` (blank = the `CBM_CACHE_DIR` environment variable, then the `CBM_CACHE_DIR` recorded in the MCP server's own `env` block in the client config, then the binary's own default).

That third step matters: the variable is normally set only inside that server record, so the server has it and a hook process never does. When the graph exists, the project has Markdown in `.ai/`, `specs/`, `.specify/` or `plans/`, and `graphify-out/.graphify_build.json` does not hold `"gitignore": false`, the note gains one line pointing at the one-time set-up in `graphify-markdown.md`; without a graph the guidance carries the same pointer. It reads files only and never runs graphify.

## `Graph-Update-Check`

**Runs:** post-task (Stop).

If `graphify-out/graph.json` is stale, asks the AI to decide whether `graphify update .` is warranted based on **structural impact** (added/removed/renamed symbols, changed exports/imports/call/inheritance relationships, new entry points, changed cross-file dependencies) — never on how many files changed: a one-file change can still be graph-relevant while a multi-file change (docs/comments/formatting-only, literal/config values, generated output) can be graph-irrelevant.  **Runs alongside Codebase Memory:** every project carries both graphs, so a CBM index no longer silences this hook — `Cbm-Read-Check`/`Cbm-Update-Check` speak for code structure while this one keeps graphify's own ground (docs, specs, papers, images, video and whole-project query/path/explain views).

Markdown counts (`graphify-markdown.md`): the newest `.md` write time in `.ai/`, `specs/`, `.specify/`, `plans/` and any top-level folder of 10+ `.md` files (git-ignored or not; dependency, build, log and agent-config folders skipped; at most 4 levels, 5,000 files, 2 s) also makes the graph stale, and the advisory then says so and asks for `graphify update .` plus the agent's own semantic pass for changed `.ai/` files.

Freshness is advisory, including confirmed staleness: Stop emits passive `systemMessage`, not a block or continuation. Bounded incomplete state remains unknown and exits 0 silently, never clean. Retain healthy rollback until coverage, semantics and endpoints pass; only then permanently delete exact proven owned obsolete copies, never via Recycle Bin. Unknown/shared/protected content remains. The hook deletes nothing and adds no ownership-based completion condition.

## `Cbm-Read-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit).

**Advisory only** — never blocks, never runs the Codebase Memory binary (measured at ~1.9 s per call, which no hook budget affords), and never writes outside its own state file. It looks at the filesystem alone: `<cache>\_config.db` to learn whether Codebase Memory MCP exists on this machine at all, and `<cache>\<project>.db` to learn whether *this* project is indexed — the same reason the Graphify hooks only test for `graphify-out/graph.json`. Completely silent when the server was never set up.

For an indexed project it says to query the graph **before** browsing files (`get_architecture` for orientation, `search_graph` for symbols, `trace_path` for callers/callees, `get_code_snippet` for exact source, `detect_changes` for blast radius) and that coverage is best-effort, never proof — `check_index_coverage` every cited path and confirm findings in the source. For a project with no index it hands over the exact one-time `index_repository(repo_path="…", mode="moderate")` call: local, seconds, and a background watcher keeps it fresh afterwards.

`UserPromptSubmit` speaks only for a prompt that needs codebase-wide understanding, using the *same* relevance test as `Graph-Read-Check` so the two can never disagree about the same prompt; one message per session per index state, so indexing during the session still gets the follow-up “now query it”. **Coordination:** every project carries both graphs, so a CBM index does not silence `Graph-Read-Check` or `Graph-Update-Check` — both keep speaking in an indexed project. The two answer different questions: Codebase Memory the code structure (symbols, call chains, blast radius), Graphify the material it alone covers (docs, specs, papers, images, video) and its whole-project query/path/explain views. One graph per question.

Known limitation, deliberately not worked around: a caller may override the project name with `index_repository(name=…)`, which a hook cannot see, so such a project reads as un-indexed here — it fails toward suggesting an index that already exists, never toward a wrong claim about the code. `.env`: `CBM_CACHE_DIR` (blank = the `CBM_CACHE_DIR` environment variable, then the `CBM_CACHE_DIR` recorded in the MCP server's own `env` block in the client config, then the binary's own default `%USERPROFILE%\.cache\codebase-memory-mcp`).

Matches one Claude JSON/Codex TOML CMM record, preserves cache/runtime/TEMP/TMP in safe CLI advice, and distinguishes root approval, separator spelling and sandbox/ancestor-access failures. No unconditional restart instruction; no CMM execution or permission changes.

**Index name, exactly as the server derives it (2026-09-30).** `<project>` follows Codebase Memory's own `cbm_project_name_from_path`: `[A-Za-z0-9._-]` are kept, each non-ASCII UTF-8 byte becomes two lowercase hex digits, every other character becomes `-`, runs of `-` or `.` collapse, a leading `-`/`.` and a trailing `-` are trimmed, and a name over 200 characters keeps 191 plus `-` and the FNV-1a hash of the whole name. The server first resolves the root through junctions and `subst` drives, which this file check does not, so a project opened through one reads as un-indexed (toward silence, never a wrong claim). The earlier rule also turned `.` and `_` into `-`, so a project such as `...\Websites\godverify.com` was looked for as `...-godverify-com.db` and reported un-indexed although `...-godverify.com.db` existed.

## `Cbm-Update-Check`

**Runs:** post-task (Stop, SubagentStop).

**Advisory only** — never blocks, never runs the CBM binary, never writes outside its own state file. It mirrors `Graph-Update-Check` step for step with the artifact swapped: `stop_hook_active` guard → the index exists → per-project cooldown → newest real work versus the index's last write. “Newest work” comes from **git**, not file mtimes, so a checkout, a formatter or an editor save does not count as a change. **Expect this hook to be silent almost always, and read that as correct behaviour:** Codebase Memory runs a background watcher that rewrites the project database incrementally, so a gap only opens when the watcher is stopped, wedged, or was never given this project.

When it does report, it names both timestamps, says to call `index_status` and re-run `index_repository` if the change is not reflected, and leaves the judgement where it belongs — **structure** (a changed symbol, export, import, call/inheritance edge or entry point) matters; docs, formatting and generated output do not, and skipping it is then the right answer. A project with **no** index at all is `Cbm-Read-Check`'s message at the start of a session where it is actionable, not this hook's at the end.

## `Install-Location-Check`

**Runs:** pre-task (PreToolUse).

Advisory only. Reads a shell command before it runs (the shared tokenizer, quotes respected, split on separators) and recognises install forms: `winget install`/`upgrade`, `choco`/`scoop install`, `pip install` outside the project's interpreter, `npm`/`pnpm -g`, `yarn global add`, `pipx install`, `uv tool`/`python install`, `cargo`/`go install`, `dotnet tool install -g`, `Install-Module`/`Install-PSResource`/`Install-Package`, `msiexec /i` and setup executables (including the CUDA toolkit `cuda_<ver>_windows*.exe` and Python `python-<ver>[-amd64|-arm64].exe` installers; NVIDIA driver packages stay unrecognised), started directly, through `Start-Process`, through `explorer.exe`, or through `Invoke-CimMethod ... Win32_Process ... Create` (its `CommandLine` literal is tokenized as data, never evaluated), `hf download` without `--local-dir`, `ollama pull`.

Each target (an explicit location option, the tool's own setting, or its default) is resolved to its physical path with junctions and symbolic links followed, on the target and on every parent. `uv tool install` and `uv python install` are judged on both the install directory and uv's executable directory (`UV_TOOL_BIN_DIR`/`UV_PYTHON_BIN_DIR`, else `XDG_BIN_HOME`, else `XDG_DATA_HOME\..\bin`, else `%USERPROFILE%\.local\bin`); `pip install --user` with an explicit interpreter uses `PYTHONUSERBASE` before `%APPDATA%\Python`; `PIP_TARGET`/`PIP_PREFIX` count as `--target`/`--prefix`. One line per package whose physical path is on the system drive and outside the project names the affected directories and prefers existing approved ecosystem roots/explicit overrides, else `G:\Program Files\<program-name>` for a new workstation program; only unavailable/unsupported locations or genuine user decisions require a question. Location approval is not installation approval. Advice also covers physical consumer paths, project temp/cache before initialization and retaining obsolete copies until verified replacement. Two cases replace the question: a location variable the resolution reads that is missing from this process but set in the user environment (`HKCU\Environment`, read-only) - the line says to set it in the command because the shell predates it; and a CUDA installer run with `-s` - silent mode always installs on the system drive, so the line names the working route instead (the graphical Custom install through `explorer.exe`, Driver and NVIDIA App unticked, a toolkit major version matching the PyTorch build: cu128 -> 12.x, cu130/cu132 -> 13.x). Silent when the location is off the system drive, inside the project, already advised for that package this session, unrecognised, or unresolvable. The only processes it starts are two bounded read-only queries (`npm config get prefix`, `python -c` printing a prefix), cached per session.

Never blocks, never approves (no `permissionDecision`), never rewrites. Rule: `global-environment-rules.md` → Install Locations. An interpreter named by an explicit path in the command is never executed: its install target is derived from where the file lives (a virtual environment's `Scripts` folder counts as its prefix; links are followed on the target); only a bare program name is queried, and it resolves through PATH like any command the user runs.

## `Cloudflare-Deploy`

**Runs:** post-task (Stop).

In Workers projects (wrangler config present), first checks **release readiness**, a deterministic filter for whether to offer deployment advice, not a completion gate and never based on hook registration/menu order, since matching-event hooks may run concurrently: stays completely silent (no reminder shown at all this Stop) unless the working tree is clean, the exact commit is known to be pushed (any configured upstream, not only GitHub), CI (if this repo has `.github/workflows`) is verified green for that exact SHA, and — when `Test-Temp-Cleanup` is installed for this project — it has reported a **fresh `clean`** result for the *current* repo state.

`clean` is the only release-ready category: `review-required`, `residue-confirmed`, `partial` and `unknown` all keep this hook silent, as do a stale fingerprint, a missing record, and any value this build does not recognize (a race on the same Stop just means it re-evaluates on the next one, never a loop). Freshness is measured against the instant the producer's scan STARTED, not the instant it finished: a candidate created after its own directory had been visited carries a timestamp earlier than a completion stamp, so a witness comparing against one accepted evidence for a path the scan never inspected.

The record also carries the detection configuration it ran under, so the witness looks for the same `EXTRA_CANDIDATE_NAMES` / `EXTRA_REVIEW_NAMES` the scan looked for — mirroring only the shipped names left residue under a configured name invisible — and it prunes by the same `pyvenv.cfg` / `CACHEDIR.TAG` markers, so a custom-named virtualenv the producer deliberately skipped no longer produces a permanent `unknown` that no cleanup could clear. That handoff is generation 3; an older record is `unknown`, never revalidated under rules it was not produced with.

The practical consequence of requiring `clean`: a project that permanently carries an untracked review artifact — a `coverage/` directory, say — reports `review-required`, so this hook now stays silent where an earlier version would have offered to deploy. Once ready, it walks the AI through a **deployment-worthiness decision** (deploy only when the task is complete, tests/typecheck/lint/build pass, the exact release commit is known, CI is green if the repo uses CI, no secrets/local-only files, unrelated changes, or disposable test cache/temp residue are included, the environment/bindings/migrations are understood, and project rules permit it — otherwise finish without deploying), **explicit environment selection** (never silently defaults to production), a **conditional Cloudflare-specific pre-deploy review** (Worker name, env vars, bindings, D1/KV/R2/Queues/Durable Objects + migrations, service bindings, routes, cron, compat flags, CLI version, build output — only what's relevant to the diff), and **required post-deployment verification** (record environment/Worker/exact commit SHA/deploy command (no secrets)/version or URL, then smoke-test or otherwise confirm it — a zero exit code alone is never treated as proof, and a failure is never hidden or blindly redeployed).

A failed or timed-out git status query is unknown, never evidence that the working tree is clean.

**Deployment acknowledgment:** after independent review, invoke the hook entry with `-Acknowledge -ProjectRoot <physical-root> -Client claude|codex -Commit <full-current-SHA> -EvidencePath <local-json> -ReviewConfirmed`. This performs no deployment, provider verification or CI operation. The repository must still be clean at that exact SHA. The evidence is a regular strict-UTF-8 JSON file, at most 64 KiB, with no linked path components. Schema 1 requires `projectRoot`, `client`, `commit`, `result` (`deployed` or `no-ship`) and a nonempty `reason`. `deployed` additionally requires reviewed `environment`, `service`, `version`, `postcheck` and an ISO-8601 `verifiedUtc` with a timezone, not in the future. These fields describe independently checked evidence, not proof manufactured by this hook. Never include secrets or raw provider output.

The immutable acknowledgment pins the evidence bytes and Wrangler configuration hash under `%LOCALAPPDATA%/HookMaker/state/CloudflareDeploy-ack-*.json`. Keep the reviewed evidence file at its original local path. A conflicting acknowledgment is refused, never overwritten; restore the exact original evidence or investigate the conflict rather than deleting history to force acceptance. Missing, edited, malformed or foreign evidence cannot acknowledge a release. Same-SHA acknowledgment survives sessions and runtime updates, but existing readiness checks still apply. Reminder cooldowns are separate per project/client/SHA/configuration; a new SHA does not inherit an older reminder's cooldown. Legacy timestamp files are not deployment acknowledgments. Complete uninstall selects only exact project-identified cooldown markers; opaque legacy markers without attributable ownership are retained, never glob-deleted. Reviewed acknowledgments remain historical evidence. Explicit acknowledgment writes collision-safe UTF-8 UTC `CloudflareDeploymentAck_*_UTC_*.log` diagnostics in the same state's `logs/` directory; logs contain outcome only, never evidence bodies. Logging failure is reported without claiming a file was written.

## `Skills-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit) + post-task (Stop, SubagentStop).

Covers the whole skill lifecycle, routed to the **active agent's** locations and never to both policies at once (`skill-policy.md`, or `skill-policy-codex-optimized.md` under Codex). Three **installed** sources are always enumerated together — a skill missed because its source was never scanned is the defect this hook exists to prevent: GLOBAL `~\.claude\skills` (Codex: `~\.agents\skills`), LOCAL `<project>\.claude\skills` (Codex: `<project>\.agents\skills`), and PLUGIN: every individual skill the active client really loads, read from its install records (per-skill discovery, below) and reported by its exact invocation name (`<plugin>:<name>` on Claude).

A fourth, **uninstalled** source — the external library named by `SKILLS_DIR` / `AI_SKILLS_DIR` (no built-in default: set one or the library half stays silent) — is searched against the current prompt. SessionStart gives the routed inventory (project + global deduped by the `name:` in each `SKILL.md`, plugin skills summarised by plugin and count) plus the closing requirement. `UserPromptSubmit` prints a prompt-matched shortlist: installed candidates with exact invocation keys and source identity (verify current host exposure before use; configuration alone proves no successful load), and library matches that are **not** installed, each with the exact `Copy-Item -LiteralPath "<library path>" -Destination "<project skills dir>" -Recurse -Force` command plus the import guidance (real folders, never junctions or shortcuts; recorded in `.ai/SKILLS.md`).

**The hook never copies, installs, refreshes, overwrites, enables or removes a skill, and never writes inside the scanned repo** — importing is an authorized operation, so discovery plus an exact instruction is the most it may do. `Stop`/`SubagentStop` **advises once by default** (blocks only with explicit enforcement) on one confirmed condition: the transcript shows a `Skill` tool call was actually made and the closing summary carries no line starting `Skills used:`. Whether a skill *should* have been used is a judgement the hook cannot make, so a session that invoked none gets a non-blocking advisory instead; an unreadable transcript is undeterminable and exits 0 silently, never all-clear.

The detector is anchored to the start of a transcript line so the hook's own instruction text can never satisfy it. Only skills **actually invoked** or materially followed belong on the line — never one merely installed, available, discovered, copied, considered or read — and `Skills used: none - <one-line reason>` is a valid answer; a skill is never forced onto a trivial task just to produce the line. Token- and time-efficient: silent when no skill source exists at all, and the two expensive enumerations (the plugin-cache glob and the ~1000-entry library walk) are cached behind a TTL while the small curated project/global directories are always read live.

`.env`: `SKILLS_DIR`, `GLOBAL_SKILLS_DIR`, `PLUGIN_SKILLS_ROOT`, `LIBRARY_INDEX_TTL_MINUTES` (default `1440`; `0` disables expiry, and the index is rebuilt anyway when the configured paths change), `SKILLS_SUMMARY_ENFORCEMENT` (`advisory` default \| `block` \| `off`). The pre-task advisory states the rule as the Skill Policy now writes it - skill use is MANDATORY, checked at task start and at every change of job kind, with each covered step done THROUGH its skill and a feature request routed to the mattpocock chain.

That is wording: the hook still copies, installs and enables nothing, and still decides for itself which skill applies. Matching is done on a skill's IDENTITY rather than its folder: the cached index records the `name:` and `description:` from each `SKILL.md` and the shortlist scores those alongside the folder, so a skill whose folder shares no word with the prompt is still found by what its description says it does. A partial word hit must now START a word, so a folder that merely CONTAINED a prompt token (`engineering` inside `glycoengineering`) is no longer offered for it, and a description's contribution is capped so incidental words in a long one cannot outrank a real name match.

Index entries carry a version, so an index written by the older format is rebuilt rather than read back with empty identity fields. With explicit `SKILLS_SUMMARY_ENFORCEMENT=block`, `Stop`/`SubagentStop` blocks once on three confirmed conditions rather than one. A skill was **invoked** and the summary names none; or the session **changed files** - the client's own record of a `Write`/`Edit`/`MultiEdit`/`NotebookEdit` call, never an assumption about what a shell command did - and carries no line either, so using no skill at all is no longer the cheapest way past the policy; or an **installed** skill this hook shortlisted for the prompt earlier in the same session was neither invoked nor named on the line, and the block names it.

Library matches are deliberately never gated: importing one is an authorized operation, so blocking on a suggestion the user never approved would force that authorization. A session that only read and answered stays advisory, `Skills used: none - <reason>` remains a valid answer to all three, and `SKILLS_SUMMARY_ENFORCEMENT` downgrades or disables every one of them. The closing demand is the offered set MINUS what has already been answered for, and the answer is written down. Without that second half the gate re-derived its demand from scratch every turn: the offered set unions every prompt's matches and never retracts, the block names six, and naming those six merely surfaced the next six - a live session banked 51 names and faced nine more forced turns whatever it said, with the user repeating one sentence each time to get their session to end.

Now a name is asked about once, whether it was invoked or explained; the block states how many are outstanding in TOTAL and carries all of them, so a single closing line can clear the whole set in one turn; and a later prompt adding new matches demands only the new ones. The check itself is unchanged; an unused, unexplained candidate blocks only in explicit block mode. Defaults are passive `systemMessage`, without continuation, and existing configured enforcement remains authoritative. Admission is tighter too: a match found ONLY in a skill's description no longer qualifies it, because one incidental word in a long description was enough to attach unrelated skills to a prompt and then require an accounting for them; a description may still strengthen a skill that already matches by leaf or `name:`.

The prompt shortlist no longer feeds itself. The `Skills used:` line this hook demands lands in the conversation, and a later prompt that quotes it - a user pasting it back, a reply-quote, a client echoing the previous turn - made the names it had just demanded score highest, so it demanded them again. A prompt with no ASCII made that total: the token split keeps only `[a-z0-9]`, so the quoted English names were the ONLY tokens in the whole prompt, and one session spent roughly forty turns on a shortlist that never converged on anything relevant.

That line is now removed before matching, while the raw prompt stays whole for the branches that legitimately read all of it - the same reasoning the file already applied to the transcript it reads at Stop. Admission is stricter too: ordinary software English such as `create`, `file`, `generate` and `design` no longer qualifies a skill on its own, because those words happen to BE some skills' own names. Raising the score floor was measured and rejected: at 3 it drops a true single-word match (a perfect hit on `codeql` scores only 2) while still admitting a name that collects 4 from two incidental words.

A score tie is now broken by where the skill came from rather than by the alphabet, which is what decided it before. The instruction and the gate finally teach the same line. The pre-task closing requirement offered `Skills used: none - <one-line reason>`, while the gate rejects exactly that whenever installed skills were shortlisted, because accounting is per NAME - so an agent that followed the instruction to the letter was blocked once and then answered with a name list contradicting the `none` it had just written.

The requirement now states that when installed skills were shortlisted the reason must NAME them; the gate itself is unchanged, and a suite assertion now ties the two so they cannot drift apart again. **Per-skill routing.** Discovery enumerates individual skills, never packages, on the client that is running and only there. Claude: every `installed_plugins.json` record (user scope plus this project's scope), each plugin's `plugin.json` `skills` field in all three shapes (absent = `skills\`, a directory, or a list of individual folders) and a single root `SKILL.md` (the Kiaro template and scientific plugins, addressed `<plugin>:<name>`), `enabledPlugins` from the user, project and local settings (no entry = enabled), and the Desktop `skills-plugin` root with its per-skill `enabled` flag (addressed `anthropic-skills:<name>`).

Codex: the plugins `config.toml` lists, at their newest cached version (several versions are reported, not hidden), the Codex `skills` folder including `.system`, `SharedAgentSkills\skills`, and `[[skills.config]]` entries that disable a skill. Enabled, disabled and explicit-only (Claude `disable-model-invocation`, Codex `allow_implicit_invocation: false`) stay distinct in the SessionStart counts, and only enabled, model-invocable skills are ever shortlisted - otherwise the Stop gate would demand an invocation the client does not allow.

The shortlist retains each candidate's exact invocation name, source kind, installation key, version and `SKILL.md` path. Configured, exposed, loaded, executed and verified are separate evidence; a recorded call proves no successful result. Failed/unavailable/unsupported outcomes remain reportable without forced retries or environment changes. Qualified accounting requires that provider's exact key; a suffix, another provider or a bare Skill call cannot prove its use. A closing explanation may separately account for a skipped candidate. This is a shortlist, not the full inventory; a missing install path, a declared path outside its plugin, an unreadable record or the 1200-skill ceiling marks discovery PARTIAL. The index is keyed to the install records, so installing, removing or toggling a plugin rebuilds it at once. The old default glob of the whole plugin cache is gone: it read uninstalled plugins and stale versions and missed root and declared skills; `PLUGIN_SKILLS_ROOT` still adds that walk when set, but cache-only definitions without authoritative installation evidence remain unknown, never enabled candidates or inferred callable aliases. Old cache formats rebuild before reuse.

**Installed-surface identity.** Claude uses the valid plugin manifest namespace, keeping registry installation keys separately. A root-source marketplace alias with an explicit skill subset exposes that subset, not the whole cache; identical same-provider alias definitions coalesce, while conflicting version/status/content or provider evidence is unknown and never shortlisted. Commands and agents are not counted as skills. Registry/enabled evidence does not prove a definition was listed or loaded by the host. No plugin/cache/config mutation is performed.

Desktop discovery supports both `%LOCALAPPDATA%\Claude-3p\local-agent-mode-sessions\skills-plugin` and the historical `%APPDATA%\Claude\local-agent-mode-sessions\skills-plugin`; a nonempty `CLAUDE_DESKTOP_SKILLS_ROOT` replaces both. Manifest enabled flags are required. Same-owner definitions are deduplicated with manifest source identity retained as a hash, verified Desktop entries are considered before large plugin packages, stale/conflicting evidence disclosed, and missing local references reported as incomplete/unknown (not shortlisted until the package is complete). Nested manifest/definition metadata invalidates the index. Limits: 64 owners/sessions, 120 child folders per session, 1200 definitions, bounded 2-second snapshot/read phases, 256 KiB per definition and 4 MiB JSON; reparse paths/unreadable evidence remain partial. These are observed supported layouts, not a universal Desktop filesystem API.

Exact prompt-named folders are considered before a large provider consumes the unchanged 1200-definition budget; this is bounded selection, not full-package coverage. Remaining installed scope and directory/time ceilings are explicitly PARTIAL. The cache retains installation/source/invocation/hash identity and the relevant selection; no registry row is presented as an actual Skill-tool load.

**Catalogue drift**, advisory only and once per session per unchanged gap: an installed definition without a current structured `catalogue/skills-*.jsonl` contract matching its client/provider/source path and explicit invocation/version/hash (up to ten named, "the rules need an update"). Historical multi-source rows are checked per source. A bare mention, another provider's qualified suffix, equal bytes, a command or an agent never proves skill coverage. Bounded catalogue reads (256 files, 16 MiB total, 20,000 rows, 2 seconds) report missing/conflicting/unreadable/capped evidence as partial, never all-clear; and a `catalogue\plugins-*.jsonl` record for this client that the install records no longer list ("the catalogue names a removed plugin"). An actual prompt beginning with `::deep-research` receives phase-specific research routing instead of the generic name shortlist. It points to current research/connected-skill companions and catalogue records, separates native commands from Gemini namesakes, and never claims runtime exposure or invokes a skill. Native `/deep-research`, ordinary mentions and quoted/fenced/pasted examples do not activate this route. Compatibility name hints also read the two companions; structured provider/kind/source/version/hash/client matching remains authoritative. See [research and operation reminders](research-operation-reminders.md).

The Spec Kit line now states the mid-task intake contract: record the request delta with requirement IDs and acceptance criteria, update the affected spec, plan, tasks and skill selection, rerun the affected gates, and let only dependent work wait. GitHub queries remain throttled, exact-SHA and bound to the same resolved remote used for repository selection and pushed-state verification (never a mismatched `@{upstream}`). Undeterminable state exits 0 silently and is never reported as verified. Only a verified live/leaked runner safety finding retains default block authority. When CI is blocked only by a confirmed **external** condition (GitHub outage, no hosted runner, an org/repo permission failure, an externally-controlled secret being unavailable, a manual approval/environment gate, ...), the agent can record an explicit, evidenced, local-only exception bound to the exact repository + pushed SHA: `-ReportExternalBlocker -Classification <category> -Reason "<evidence>"`.

**Eligibility is conservative:** an exception may only be recorded when the observed GitHub run state is non-code-failure identifiable without reading logs — still pending / a manual gate, or a completed run whose conclusion is `cancelled`/`timed_out`/`stale`/`action_required`. A completed `failure`/`startup_failure` is **never** eligible (the hook cannot tell a real code/test/build/lint failure from an external one without trusted evidence), regardless of classification (including `other-external`); the classifications describe *why*, but cannot excuse a generic `failure`.

**One narrow, evidence-backed exception is auto-detected:** an account **billing/payment/spending-limit** block. When Actions cannot start for that reason GitHub reports every run as `failure` even though no job ran — status alone is indistinguishable from a real failure, which is why it is otherwise refused. The distinguishing evidence is GitHub's **own check-run annotation** (*"recent account payments have failed or your spending limit needs to be increased"*), read from the check-runs annotations API — never inferred from step counts (a broken workflow file also yields zero steps but a *different* annotation, so it remains a failed/unproven CI finding, advisory by default).

It is recognized only when **every** failing check-run for the commit carries that annotation, verified **pagination-safe** (all check-run pages and all annotation pages are read up to a strict bound, `total_count` is confirmed against the number actually fetched), and it **fails closed** on any query error, a truncated/unverified page, an oversized set beyond the bound, or a single failing check-run without the annotation. This case is auto-recorded as `account-billing` (no `-ReportExternalBlocker` needed), reuses the same throttled recheck/retire machinery, and still never marks CI green — no commit can clear a billing block.

Recording **always queries the exact-SHA CI state first** — refused if already green, refused on a genuine completed failure, refused if CI can't be queried — and captures a non-secret CI fingerprint (`databaseId`/`attempt`/`workflowName`/`status`/`conclusion`/`updatedAt`, so a rerun is distinguishable). It never marks the commit verified/green; **while active, Stop emits a non-blocking "CI NOT VERIFIED GREEN" notice — once per session per blocker** — so the final task context cannot misrepresent CI as successful.

Once, because on Claude Code a Stop `additionalContext` re-invokes the model: emitted on every Stop, this notice re-invoked the agent on every Stop (answer, stop, re-invoke, answer, until the user interrupted) in every repository with a billing block, which stays valid for a day. ## `Secrets-Check`

**Runs:** pre-task (SessionStart) + post-task (Stop).
Secrets-Check interprets one matched outer single/double quote pair when classifying credential values and matching leaks, so a quoted token cannot evade strong-format checks or bare-token working-tree/index/outgoing matches. Original registry values and source metadata are preserved verbatim; the shared hook configuration parser is unchanged. Values are never executed, interpolated, or escape-expanded. This is not a complete dotenv parser: multiline values and inline-comment/escape processing remain outside this normalization.

The mixed-case entropy guess uses case-sensitive uppercase/lowercase tests. A long lowercase/uppercase-only identifier is not a mixed-case credential. Unverified custom model identifiers remain Unknown/advisory unless stronger evidence exists; verified public routing keys may be listed individually in this hook's own PUBLIC_CONFIG_KEYS. No global MODEL_* exemption; explicit SECRET_KEYS, credential key semantics and definite token/private-key formats still win.


Safely scans real `.env*` files throughout active project subtrees (templates, dependencies, builds, caches, assistant runtimes, and reparse points are pruned). Lifecycle events retain registry/placeholder/unused advisories. The leak scan merges and deduplicates git **working-tree and index** matches (`git grep` + `git grep --cached`), so a value staged then cleaned from the working copy only — or committed and later edited away locally without staging that edit — is still caught. During native pre-push it **additionally scans the exact commits about to be pushed**, resolved from git's real pre-push ref-update stdin (`<local ref> <local sha> <remote ref> <remote sha>`): a secret sitting in an outgoing commit is caught even when the working tree and index are already clean.

The outgoing-history scan does **not** exclude `.env*`/`secrets.md` — a committed real `.env` or registry file in outgoing history is itself a leak, even if it was later deleted/untracked before the push. New branches (all-zero remote sha), deletions (all-zero local sha), force-pushes/non-fast-forwards, and multiple refs in one push are all handled. It **fails closed**: the whole range is scanned in bounded batches (no commit cap), and if any ref range cannot be resolved (unresolvable remote sha, `rev-list`/`git grep` error) the push is **blocked** with a safe incomplete-scan message rather than treated as clean.

Native pre-push blocks only confirmed indexing/leak/outgoing/incomplete-scan risks; advisory-only findings exit successfully. Secret values are never printed. The leak scan is grouped **by value, not by key**: several keys holding one value (`ADMIN_EMAIL`/`OWNER_EMAIL`/`KYC_ADMIN_EMAIL`) produce one finding naming all of them, instead of the same file list repeated per key. **Classification precedence:** `SECRET_KEYS` override → *definite* credential value formats (private key, JWT, `sk_live_`, `ghp_`, `AKIA`, `user:pass@host`, credential query params) → credential-like key semantics (`*_PASSWORD`, `*_TOKEN`, `*_SECRET`, `API_KEY`, …) → `PUBLIC_CONFIG_KEYS` override → the *entropy heuristic* (24+ chars, no whitespace, mixed case + digit) → inferred public config → Unknown.

**Both overrides are read from the hook's own `.env`**, beside the installed script (`<project>\.claude\hooks\Hook-Maker\Secrets-Check\.env`) — never from the scanned project `.env`, which is the input being classified: letting that file declassify its own keys would defeat the guard. The "Classification unclear" advisory prints the full path, and installs/updates never overwrite or delete it. The two value tiers are deliberately unequal: a definite format **identifies** a credential and can never be declassified, but the entropy heuristic only **guesses**, and it fires on values that are public by design — a Turnstile **site** key, a Cloudflare account ID, a publishable key — so it sits *below* `PUBLIC_CONFIG_KEYS` and can be corrected per key.

Native pre-push has a separate hook-local config at `<project>\.git\hooks\Hook-Maker\Secrets-Check\.env`; configure each installed runtime explicitly. For a verified public model identifier, add the exact key (for example `MODEL_1_ID`) to `PUBLIC_CONFIG_KEYS`, preserving existing settings; never use a blanket `MODEL_*` exemption. `API_KEY`, credential-key semantics, definite tokens, private keys and credential-bearing URLs remain Secret even if listed. Stale registry cleanup removes only a complete, unchanged hook-generated block whose stored value and source exactly match the currently discovered PublicConfig entry. User edits, notes, different/credential values and ambiguous blocks are retained byte-for-byte.

Its default answer is unchanged (still Secret with no override). An e-mail address is excluded from the heuristic outright; an address under a credential-named key (`SMTP_PASSWORD`) is still Secret via key evidence. **Limitation:** `Secrets-Check` is a value-based leak guard, not a full entropy/pattern/history secret scanner — the only source of searchable values is the active `.env*` files. `secrets.md` is read to check whether a key is documented and for the unused-key scan; its recorded values are **not** themselves leak-scanned, so a secret that lives only in `secrets.md` or only in the deployment secret store is invisible to it.

A secret introduced and later removed from outgoing history **and** every current source is likewise no longer known and cannot be matched; use an established dedicated historical-secret scanner in CI for unknown credentials. Inside a git work tree the registry is always the REPOSITORY root's `secrets.md`, where the rooted `/secrets.md` ignore rule applies, even when the session's working directory has drifted into a subfolder; a folder outside git is its own root, as before. Secret values are handed to `git grep` through a per-scan pattern file under the user's local state (removed after the scan), never as a command-line argument, so they do not appear in process listings or process-creation audit logs.

## `Ignore-Rules-Check`

**Runs:** pre-task (SessionStart) + post-task (Stop) + native Git pre-push.

Auto-adds required local/private patterns to `.gitignore`, extracts additional paths from explicit local-only/never-commit project rules, and advises once per fingerprint while required fixes remain; lifecycle and native pre-push findings exit 0 by default. Default public template files (`.env.example`/`.env.sample`/`.env.template`/`.env.dist`) are intentionally allowed to stay tracked via `!`-negation exceptions — they are never reported as a protected path that must be untracked, while real env files (`.env`, `.env.local`, `.env.production`, ...) remain protected.

Patterns are written and compared in **insertion order**, never alphabetically sorted (an alphabetical sort would silently break every negation exception, since `!` sorts before `/`), and a path whose effective `git check-ignore` match is a negation is always treated as explicitly allowed. **A negation that is already effective is never re-added.** Whether one is doing its job is decided by asking `git check-ignore` about the path, not by comparing line positions against every other managed pattern - the old comparison condemned a correctly-anchored negation whenever any unrelated managed positive (`/plans/`) happened to sit later in the file, and since this hook appends its own block at the END it kept creating that condition itself, duplicating the block on every run until the user moved everything to the tail.

A project that deliberately re-protects one of those paths with its own positive `EXTRA_PATTERNS` entry still wins. Project installs create a deterministic pre-push chain: Ignore → Secrets → Utf8 → preserved previous hook. Large-File-Check remains advisory and never decides whether a push may proceed. Optional extra patterns can be set in `.env`. Inside a git work tree it always works on the REPOSITORY root (`git rev-parse --show-toplevel`), never on a subfolder the session's working directory drifted into - before this, such a drift planted a stray `.gitignore` full of rooted patterns in that subfolder; outside a work tree it does nothing, as before.

Native execution uses one checked root query and the index inventory (including staged additions); the staged-name query runs only after a protected match. Path batches retain the 8,000-character bound. Fixed stderr markers announce actual repository, index and batch transitions; the canonical wrapper announces Ignore, Secrets and UTF8 stage starts. They contain no paths, refs, arguments or contents, do not claim success and are not periodic heartbeats. Lifecycle output, raw ref-update stdin replay, exact failure codes, short-circuit order and preserved user hooks stay unchanged; no timeout is increased.

Ignore patterns harvested from the project's own rule files (AGENTS.md, CLAUDE.md and the agent rule folders) are tracked project text, so by default (`RULE_FILE_PATTERNS=advisory`) they are only reported, once per set - never written into `.gitignore` and never grounds for a push block; `write` adds them without protecting them, and `write-and-protect` restores the earlier behaviour. The built-in set and `EXTRA_PATTERNS` are unchanged.

## `Dependency-Version-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit) + post-task (Stop, SubagentStop).

**Advisory only** — never modifies manifests/lockfiles/workflows/Dockerfiles, never runs an upgrade, never auto-merges Dependabot PRs, never blocks completion. SessionStart reports version-freshness findings for ecosystems actually detected in the project: real `npm outdated --json` (exits 1 when outdated packages exist — treated as success, not a failure) and, for Python, `python -m pip list --outdated --format=json` run through **this project's own interpreter** (`.venv`/`venv`, or `VIRTUAL_ENV` only when it points inside the project) rather than whatever `pip` resolves to on PATH — the machine's global packages are not this project's dependencies, and reading them produced findings that were not merely noisy but backwards (a project venv can be *ahead* of global).

A project with Python manifests but no environment of its own is reported **incomplete**, never answered from global. The pip probe gets **120 s**, not the 20 s default every other quiet command gets: the same command was measured at 32 s (exit 0) on a venv created with `--system-site-packages`, where pip asks PyPI about every package the environment can see rather than the handful this project declares, so at 20 s it was killed and reported as a failed check on every single run - a permanent UNKNOWN on any project with a wide venv.

Project discovery uses the same bounded, root-relative advisory scope described above. Partial discovery uses neither a cached complete report nor a package-manager query. Every package-manager query is clamped to the remaining registered hook deadline, including npm/Go; the pip request ceiling is also clamped, never guaranteed 120 seconds.

`npm outdated` and `go list -u -m all` keep the shared default: neither has been measured on a tree large enough to justify moving it, and a guessed timeout is not a contract. Each failure message is built from the same argument array the call passes, so it can never name a command that was not the one that ran. These classify each update as patch/minor/major/prerelease; GitHub Actions get a static known-minimum-major check on `uses:` refs; runtime pins (`.nvmrc`/`.node-version`/`.python-version`/`engines.node`) and Docker base images (`FROM` tags) are checked against a small known-EOL list, and a floating/untagged image is flagged as non-reproducible.

Ecosystems without a verified, reliable JSON command here (pnpm, Yarn, Bun, Poetry, uv, .NET, Java/Gradle/Maven, Rust/Cargo, PHP Composer, Ruby Bundler) are detected and reported as an **incomplete** check with the exact command to run manually, rather than guessing at an unconfirmed schema or a fragile text-table parse — it never claims a dependency is current when a check could not run. `UserPromptSubmit` reuses the cached findings and additionally injects "prefer the latest stable compatible version, not a prerelease" guidance when the prompt looks like it's adding a dependency/framework/runtime/build tool/action/Docker image or starting a project from scratch.

Cached per-project by a fingerprint of detected ecosystems + manifest/lockfile/workflow/Dockerfile/runtime-pin **content** hashes (not just presence), so an unrelated task stays fast while any real change triggers a fresh scan; default cooldown is 7 days. Complements `Dependabot-Check` (existing PRs) and `Github-Baseline-Check` (CI/Dependabot baseline structure) without duplicating either.  `Stop`/`SubagentStop` replay the still-unanswered findings **once per session**, from the cached report only — no scan, no `npm`/`pip`/`go` invocation, no upgrade, and **no block on any event**: whether to upgrade is the user's decision and a judgement the hook cannot make.

What changed is the output contract, not the scanning — the report now asks the closing summary to carry a line starting `Dependency decisions:` answering each finding with `<name>=update\|keep\|defer (<reason>)` (or `Dependency decisions: none - <one-line reason>`). That line is *requested*, never enforced: an unanswered finding is reported as an unreviewed risk, not as a refusal to stop. Steering V48: the replay asks for each finding to be updated now to the latest stable release, or to the nearest version below it that does not break (the breaking version and failure recorded); a pip finding the venv inherits from a shared global install is marked `[global install]` and is updated in that global install; only a recorded reason (intentional pin, advisory on the newer release, unsupported runtime, licence change, OS-managed tool) leaves one in place.

`.env`: `COOLDOWN_MINUTES` (default `10080` = 7 days), `MAX_FINDINGS` (default `12`), `CLOSING_REMINDER` (`1` default; `0` keeps the hook pre-task only), and `PYTHON_EXECUTABLE` - the full path of a shared base interpreter this project deliberately runs on when it owns no venv. That last one is the only way a non-venv project is ever inspected: it is honoured because the PROJECT named it and the path verifies, never because `pip` happens to resolve on PATH. **Findings are scoped to the project, not to the machine:** with inherited system site-packages `pip list --outdated` reports everything installed, so the report is restricted to the dependencies this project DECLARES (requirements*.txt, PEP 621 and poetry `pyproject.toml`, `Pipfile`, `setup.cfg`) plus their transitive closure, asked of the same interpreter through stdlib `importlib.metadata`.

A scope that cannot be determined is reported as incomplete rather than widened back to everything, and packages excluded as the machine's are silently not reported - they were inspected and consciously left out, which is the opposite of missing coverage.

## `Test-Temp-Cleanup`

**Runs:** pre-task (SessionStart) + post-task (Stop; SubagentStop opt-in).

**Detector/advisory by default; it deletes nothing.** Residue and incomplete cleanup evidence are not default completion gates. Only an independently confirmed unsafe-deletion/data-loss condition can be a safety gate; this detector does not authorize deletion. There is no deletion feature and no setting that can enable one: the hook never deletes, moves, renames, truncates, stages or otherwise mutates any project file, never runs `git clean`/`reset`/`rm`/`add`/`restore`/`checkout`, and never touches the git index. The only thing it writes is bounded metadata into Hook Maker's own private state directory under `%LOCALAPPDATA%\HookMaker\state` — never candidate file contents, secret values, prompts, tool inputs or raw logs.

The **agent** performs any deletion, with its normal tools, after independently confirming each candidate. It recognizes disposable test cache/temp residue (`.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.hypothesis`, `.nyc_output`, `.jest-cache`, `.vitest-cache`, `.test-tmp`/`.test-temp`, and `__pycache__`/`*.pyc`/`*.pyo` **only** when they genuinely appeared during this session — a pre-existing one is `ambiguous`, never disposable) and diagnostic/review artifacts (`coverage`, `htmlcov`, `test-results`, `playwright-report`, `blob-report`, `TestResults`, `.coverage`, `coverage.xml`).

SessionStart records a metadata-only baseline (relative path, kind, link state, size, mtime, git state) plus the scan's own completeness and its exact partial causes, staying silent unless that scan was itself partial. Stop rescans under the same bounded rules, compares against this session's baseline, and gives every candidate exactly one classification — `likely-disposable` (a *description*, never deletion approval), `review-or-diagnostic`, `protected`, `ambiguous`, `unknown-git-state`, `partial-or-unreadable`.

Hard protections, none of them overridable by config: the hard-prune set (`.git`, `.ai`, `.claude`, `.codex`, `.kiro`, CI and package-manager runtime state that would otherwise blow the scan ceilings on its own - `.ci-runner`, `.cache` - and dependency/build roots such as `node_modules`, venvs, `vendor`, `target`, `dist`, `build`, `out`) is never surfaced and never descended into — a directory is also pruned by a MARKER FILE it contains, so a name list cannot miss it: `pyvenv.cfg` (PEP 405) means an unconventionally named virtualenv like `spotdl-env` is pruned exactly like `.venv`, and `CACHEDIR.TAG` means any tool's regenerable cache is skipped whatever it is called.

A reparse point is never probed for a marker; symlinks/junctions/reparse points are never followed; nothing outside the canonical project root is surfaced; tracked and staged paths are protected; and anything with incomplete metadata or unknown git state is never described as disposable. The result is one of five categories — `clean`, `review-required`, `residue-confirmed`, `partial`, `unknown` — and **a partial scan can never report `clean`**: coverage limits and read failures resolve to `partial`, missing/unusable git or baseline evidence to `unknown`.

A candidate it already surfaced as likely-disposable on an *earlier* Stop of this session that is still present becomes `residue-confirmed`, which is evidence its instruction was not resolved, **not** a claim that the hook confirmed the path is safe to delete. `residue-confirmed` and `review-required` are advisory, exit 0; partial/unknown state must exit 0 silently, never report clean. Delivery is fingerprinted on the bounded evidence, so unchanged evidence never loops while materially changed evidence re-surfaces immediately. Configurable in `.env`: `MAX_SCAN_ENTRIES` (default 15000), `MAX_SCAN_DEPTH` (12), `MAX_FINDINGS` (20 — truncates the report list only, never the scan), `ENABLE_SUBAGENT_STOP`, and `EXTRA_CANDIDATE_NAMES`/`EXTRA_REVIEW_NAMES`, which are **detection hints only** — config can add something to look at, never mark something safe to delete and never weaken a protection.

Baseline and reporting state use a project key plus a hash of the exact session ID, so simultaneous sessions cannot overwrite each other's start or repeat-suppression state. First publication is atomic and never replaces an existing baseline; repeated/resumed SessionStart preserves even partial or malformed original evidence. A matching legacy baseline remains readable only when scoped evidence is absent; missing, foreign or malformed evidence never proves historical absence. Completion's survivor advisory reads the same scoped baseline, with the same matching-legacy fallback. Supported updates include the helper without changing events, timeouts or explicit configuration. Complete uninstall retains baseline/reporting history for surviving readers and retires only the owned project coordination signal; no session-history glob is deleted.

The coordination record `Cloudflare-Deploy` reads is written on every Stop, even when the message itself is suppressed (see above). `.ai/RESEARCH/` is never residue: research notes survive every cleanup.

## `Test-Plan-Check`

**Runs:** pre-task (SessionStart, UserPromptSubmit).

The **before** stage of the three-stage test-health architecture (`Test-Plan-Check`, `Test-Run-Guard`, `Test-Completion-Check`). **Detector + advisory: it never executes a test, spawns a process or invokes a runner, never writes anything into the project (its only state lives under `%LOCALAPPDATA%\HookMaker\state`), and never blocks** — it emits advisory context or nothing at all. SessionStart surfaces the applicable policy once per project/state. That always-emitted policy block also carries the **verification cadence** — light checks only while code is still being written, the heavy pass (full suites, matrices, integration tiers, every guarded run) exactly once after all edits are complete, then fix everything that pass reported together and re-run once, never a re-run because one more file changed — and the **test-optimization-before-any-run** rule: everything that executes code to produce evidence is a test whatever it is called, and none of them may run before it is fully optimized - new tests written optimized, changed tests re-optimized, and EXISTING suites optimized before they run again, with validity never traded for speed and the before/after record kept in `.ai/TESTING_NOTES.md`.

A fourth bullet carries the **no-orphaned-test-process** rule: a test is never started detached without a recorded pid and a bounded owner, the turn never ends while a run the agent started is alive, an interrupted wait yields no result so the tree is killed first, and a survivor sweep runs before finishing and after every subagent reports. `UserPromptSubmit` is **relevance-gated**: it reacts only to prompts that are actually about tests, CI, runners, hangs, timeouts, parallelism, workers, CPU/memory, sleep/polling or test cleanup — ordinary prompts get nothing, and silence is by far the common case.

A **standalone** `::deep-debug` token (never the prose "deep debug") also passes the gate and extends the same advisory with the deep-debug test-health plan requirements under the same fingerprint gate; that is detection only — the hook never executes a codeword, slash command or skill. Reported risks are only ever things it can **point at**, with a file and line, in the repository as it exists right now: a fixed blind sleep at or over the blind-wait ceiling inside a test file, an unbounded wait, an unbounded polling loop, a child process started with no visible wall/idle bound.

Never a theoretical warning. The scan is an iterative directory walk that **prunes** excluded trees (`.git`, `node_modules`, `.venv`, `dist`/`build`, `graphify-out`, `.ai`, `.claude`, ...) and never follows a junction or symlink; separate ceilings bound directories visited, candidate test files inspected, KB read from any one file, total wall time and findings emitted, and hitting any of them — or an unreadable directory — makes the advisory say the scan was **partial** rather than implying the whole repository was covered.

Token-efficient by design: a compact fingerprint (git state plus a signature of what the scan actually saw) and a cooldown keep an unchanged repository from re-warning on every prompt, while a **changed** state is reported immediately, ignoring the cooldown — that is the whole point. Output goes through the shared `Write-HookResult` adapter rather than a hand-rolled client branch, and no path ever emits `decision:block`. `.env`: `TEST_PLAN_COOLDOWN_MINUTES`, `TEST_PLAN_EXTRA_KEYWORDS` (project vocabulary on top of the built-in relevance set), `TEST_PLAN_ALWAYS_REPORT` (ignore the cooldown; for debugging the hook itself), the scan ceilings `TEST_PLAN_MAX_DIRS` / `TEST_PLAN_MAX_FILES` / `TEST_PLAN_MAX_FILE_KB` / `TEST_PLAN_MAX_SCAN_SECONDS` / `TEST_PLAN_MAX_FINDINGS`, and `TEST_PLAN_MAX_BLIND_SLEEP_SECONDS` (`0` disables the check), which deliberately mirrors `TEST_GUARD_MAX_BLIND_SLEEP_SECONDS` in `Test-Run-Guard` — same value and same `0`-disables meaning, so the before-stage and the during-stage cannot disagree about what a blind sleep is; change one, change the other.

An invalid value is reported once in plain text and the default is used: a malformed setting must never block or crash a session. PowerShell risk detection parses executable syntax: quoted samples and diagnostic strings are ignored, while quoted command invocations and executable interpolation remain visible. Oversized files, failed UTF-8 reads and unparseable PowerShell also make coverage partial. The advisory also states WHERE the heavy pass runs: every test that can run in GitHub CI runs there on the pushed commit, local execution stays in the light loop, a suite the workflow does not cover is fixed by extending the workflow rather than running it locally, and the local fallback needs a live `gh` query plus a timestamped record in project memory.

## `Test-Run-Guard`


**Runs:** pre-task + post-task (PreToolUse, PostToolUse).

Clean and untracked-only acquisition uses three Git launches with the exact ordinal v1 fingerprint, including space-path quoting. Initially tracked-dirty trees retain the four-launch route. Present-empty Git configuration is preserved from the environment block on both hosts; absent pairs refuse. The four-second admission deadline, physical-root checks and exact-root approval remain unchanged. See the [recovery contract](TEST-HOOK-RECOVERY.md).

**Literal binding preflight:** an already-guarded invocation with a missing, blank, unusable or stale `-ProjectFingerprint` receives an advisory correction before an observation is written; the hook exits 0 by default. The response supplies the current literal fingerprint and an exact correction changing only that parameter; command, working directory, wall/idle limits, workers and all other options are preserved. No tool input is rewritten and no permission is granted. A literal `-WorkingDirectory` outside hook cwd receives an explicit advisory: run from that project's session context and obtain its fingerprint, never bind its receipt to this project. Dynamic or unsupported identity/cwd syntax remains advisory with no fabricated observation. Direct standalone callers must now pass a nonempty fingerprint: the runner exits `3` before sibling initialization, capture files, child startup or evidence publication when omitted/blank; it never guesses one. Existing raw-command replacement still supplies the identity. Historical receipts/observations are not backfilled, and completion matching/supersession/one-to-one assignment are unchanged.

**Repository-state provenance:** `projectKey` addresses files, never proves a tree state. Git ownership refusal/failure in a repository gives explicit `unavailable` state and an empty `repositoryStateFingerprint`; recognized test commands receive advisory guidance without an invented observation, path fingerprint or automatic trust/ACL change; the standalone runner's validation and exit codes are unchanged. Deliberately non-Git workspaces retain explicit degraded `nonrepository` compatibility, not CURRENT repository evidence. Observations carry this provenance separately from the existing binding fields. Sanitized access diagnoses distinguish ownership, missing Git/repository, permission, timeout and concurrent changes. Explicit owner-confirmed, revocable exact physical-root approval is supported by `scripts/Set-RepositoryTrust.ps1`; no global configuration/ACL change or project-selection approval. Status lines are sorted with case-sensitive ordinal ordering, independent of host culture and NLS/ICU differences; raw lines and both-snapshot change checks are preserved. Acquisition shares one four-second overall budget across physical/approval checks and at most four Git processes: the first `rev-parse --show-toplevel HEAD` returns exactly root plus HEAD. A clean first v1 status uses a second v2 status with branch OID for the second HEAD/status, reducing clean acquisition to three launches; dirty acquisition retains the exact four-launch legacy path and fingerprint. Missing, duplicate or malformed OIDs and newly dirty status are refused. No dirty v2 path conversion, cached state, removed check or longer deadline is involved; each bounded child receives the remaining milliseconds, including a fractional final second. A final budget check rejects successful last reads or identity/approval validation completing at or after four seconds before any fingerprint is published. Exhaustion/process timeout reports `gitTimedOut`; genuine launch failure stays unavailable, with no cached/guessed identity. An update may change a dirty tree's old fingerprint: obtain a fresh literal without rewriting historical evidence. The standalone runner recomputes the same HEAD + sorted-status fingerprint before captures/child startup and propagates only approved command-scoped Git configuration to the actual child. See [exact-root approval](TEST-HOOK-RECOVERY.md#explicit-exact-root-approval).

**Ownership is not a numeric PID.** When a Windows Job exists, its membership is the sole authority for resource accounting, completion and termination; sampling pins each process handle and rechecks membership before counting resources. A failed Job query or termination is unproven, never a PPID/recursive-kill/taskkill fallback. Without a Job, the runner requires the recorded root birth and valid direct-parent birth edges, uses the bounded shared helper (depth 8, 512 nodes), and kills only verified retained handles. Missing identity or incomplete coverage fails closed. `hooks/_processtree.ps1` is shipped as the Immutable companion `scripts/_processtree.ps1`; canonical source uses the same helper. Resource ceilings, events, receipt schema and failure recovery are unchanged.

The **during** stage of the three-stage test-health architecture. `PreToolUse` advises on unbindable literal invocations and recognized raw test commands without a bounded runner, supplying the exact safer replacement without granting permission. Unsafe name/wildcard process-stop requests retain a data-loss gate. `PostToolUse` is a detector/advisory: it reads the runner's structured result and reports timeout, kill, leak or nonzero exit without converting a historical failure into a block. Verified live/leaked processes are handled by the completion safety path. **Why the hook does not watch the run:** the hook process returns in milliseconds and is gone long before a suite finishes, so the watchdog lives in `scripts\Run-Tests-Guarded.ps1`, which owns the child process for its whole life; the hook only decides whether that owner exists and later reads what it recorded.

**Recognition is conservative and structured.** The command is treated as data: tokenized with quotes respected, split on separator tokens, and matched on the program token plus, where it disambiguates, its subcommand. It is never evaluated, never concatenated into a shell string and never handed to `Invoke-Expression` — this hook starts no process at all. A `pwsh -Command '<string>'` payload is deliberately **not** inspected, because recognising it would mean parsing a shell, so it stays silent; anything not positively recognised produces total silence, since a false positive here would block real work.

**This tool's own hook scripts are never test commands.** `Test-` is an approved PowerShell VERB meaning "evaluate a condition", so `Test-Plan-Check.ps1`, `Test-Run-Guard.ps1` and `Test-Completion-Check.ps1` all matched a pattern that was never about them - and the guard was fencing off `Test-Completion-Check`'s own printed recovery command, where wrapping it filed a new permanent block. A script whose parent directory is named after it AND which sits under a `hooks` directory is excluded; this repository's real suites (`scripts\Test-Wizard.ps1`) and a project's own `tests\Test-Foo\Test-Foo.ps1` are not.

It also advises against a direct **blind wait**, exit 0 by default: — a fixed literal delay at or above the ceiling (`Start-Sleep -Seconds N`, `sleep N`, `timeout /t N`), or an always-true poll loop that sleeps with no visible deadline — and answers with a deadline-bounded readiness check. That detection inspects only **top-level** tokens, so a delay nested inside a quoted string (`bash -c "sleep 300"`) is never parsed, a short backoff below the ceiling is never touched, and GNU `timeout 300 <cmd>` bounds a command rather than being a blind wait.

A deny or advisory also states the bounds the replacement already enforces (bounded runner, the documented native timeout where the framework supports one, wall/idle limits, one shared worker ceiling, process-tree cleanup, exit-code propagation, no ad hoc sleeps) and — only when the command **visibly** writes textual output to a file — advises explicit UTF-8 output using officially documented syntax only (PowerShell `-Encoding utf8`, Python `PYTHONUTF8`/`PYTHONIOENCODING`); it never invents an encoding flag, and validating files stays `Utf8-Encoding-Check`'s job.

The same note closes with the **verification cadence**, which decides *when* the replacement belongs: while code is still being written the suite is deferred to the single heavy pass after all edits and only light checks run until then, and the replacement runs now only when this is that final pass, when the run itself is the work (`::test-audit` timing, a suite-only failure), or when the user asked for it. The same note adds the other two preconditions a run must already meet: the suite is optimized before it may run at all, and the guarded runner is its only permitted owner, never a background job.

That is guidance on the note only — recognition and replacement commands are retained, while nonsafety denials become advisories by default. **Coordination state for `Test-Completion-Check`** is written per run, keyed by `<projectKey>-<runId>`, so two concurrent guarded runs in one project never overwrite each other's evidence: `TestRunGuard-observed-<key>-<runId>.json` is written on `PreToolUse` for **every** recognised test command — blocked, advised or already guarded, recording which — and is what lets `Test-Completion-Check` refuse a "tests passed" claim when nothing produced a result; a blocked command is recorded too, because the intent to test is what creates the obligation to show evidence.

`TestRunGuard-result-<key>-<runId>.json` is written by the runner itself through the per-run `-ResultPath` this hook puts in the replacement, and `PostToolUse` pairs a result to its observation by run identity. The `active` marker is deliberately **not** written here: only the runner knows its own live pid, an absent file means "not evaluated" and is therefore silent, whereas a guessed pid would be a false completion blocker on a recycled process id. **Worker ceiling:** the runner resolves one effective cap — this project's value folded with the shared resource-aware budget `max(2, min(8, cores-2))` and any stricter pre-existing value, so it only ever tightens — and exports it as `HOOKMAKER_MAX_TEST_WORKERS` into the child's environment.

It does **not** rewrite the command's own worker flag, since every framework spells that differently (`pytest -n`, `jest --maxWorkers`, `vitest --maxThreads`, `go -p`, `cargo -j`, `dotnet -m`, PowerShell `-ThrottleLimit`) and the command that oversubscribes usually carries no flag at all; so the cap binds inside a runner that reads the variable (this repository's `scripts\Run-Tests.ps1` does), and a framework that ignores it stays advisory. **Progress, not liveness:** a run counts as progressing while *any* of output bytes, cumulative CPU in the owned process tree, owned tree membership, or an optional heartbeat file advances; only when none of them move for the idle window is it terminated — so a silent but CPU-busy computation is never killed for idleness, and only the wall and memory ceilings bound it.

`.env`: `TEST_GUARD_WALL_TIMEOUT_SECONDS` (default `1800` — a ceiling, not an expected duration), `TEST_GUARD_IDLE_TIMEOUT_SECONDS` (`300`; `0` disables), `TEST_GUARD_HEARTBEAT_SECONDS` (`10`), `TEST_GUARD_MAX_MEMORY_MB` (`0` = disabled on purpose: there is no universal correct value, and a wrong one kills valid work on a large suite), `TEST_GUARD_MAX_WORKERS` (empty = the shared budget), `TEST_GUARD_MAX_BLIND_SLEEP_SECONDS` (`30`; `0` disables), `TEST_GUARD_EXTRA_TEST_COMMANDS`, `TEST_GUARD_NEVER_GUARD` (takes precedence over recognition), `TEST_GUARD_ADVISORY_ONLY` (`0`; advisory mode annotates a command with context only and never approves it - no `permissionDecision`, so the user's own permission prompt still applies).

An invalid value is reported once and the default used: nonsafety guidance remains advisory, never an unconditional blocker or permission grant. The advisory opens by saying a suite GitHub CI runs is not run here - push and read the result for that SHA - so the local guarded command it hands over is understood as the exception (a light single-test run, or the heavy pass once a live `gh` query has shown CI cannot execute it). The recognition logic, the deny, the injected run id and result path, and the replacement command itself are unchanged; the hook never decides whether CI is available.

**An asynchronous run that has not finished is DEFERRED, never accused.** On a client whose shell call returns before the child does (the installed Codex app's `exec_command`), the result document legitimately does not exist yet at `PostToolUse`, and the detector used to announce that the run left no evidence. Deferral is granted only on an owned active marker that matches this run/command/repository AND whose recorded owner is provably the process running right now - pid plus its recorded start time, plus the executable when both sides know it, with no pid-only path.

A missing field, a missing owner, a recycled pid or an unrelated process stays UNKNOWN and keeps the ordinary warning; deferral never means passed. The client envelope is used as it actually is - that app normalizes shell events to `tool_name: Bash`, exposes only `tool_input.command` and returns captured stdout as `tool_response`, carrying no execution-session id and no exit metadata - so nothing is reconstructed from stdout, and a structured execution session is bound only when the envelope agrees with this client session.

See [test-hook identity and recovery](TEST-HOOK-RECOVERY.md) for explicit user activation, literal argument identity and validated historical incident recovery. Recognition reads the command's TEXT, so a span of it that is content rather than instruction is removed before anything is recognised: the body of a heredoc fed to a program that does not execute its standard input, and every PowerShell here-string, which is a value in the language itself. Who RECEIVES the text is what decides - a heredoc handed to Python is Python source and one redirected into a file is bytes, neither of which can run a suite, while a heredoc handed to a shell really is shell and keeps its body scanned, including when that shell is reached through a wrapper such as `sudo` or `env`.

Without the distinction, a command that merely WROTE a file whose prose named a runner was refused, and the replacement it printed was assembled out of that prose; each refusal also filed a completion record that nothing could satisfy, because no test had run. An unknown program is treated as not-a-shell and an unknown wrapper as not-transparent, so the failure direction is a false positive and never a missed unbounded run. A NEWLINE is a real separator as well: the separator list had always named it, but the tokenizer could not emit one, so every line of a multi-line command collapsed into a single segment and a command written under another could not be recognised at all.

Leading shell assignments (`CI=1 pytest ...`) are skipped when recognising the program and repeated in front of the printed replacement; a segment that is only assignments (`F=x.ps1; rm $F`) is never a command.

**CI runner stops (2026-09-30).** On PreToolUse a command that stops CI runners by name or wildcard - `taskkill /IM Runner.Listener.exe`, `Stop-Process -Name Runner*`, `Get-Process Runner* | Stop-Process`, `pkill`/`killall` naming `Runner.Listener`, `Runner.Worker` or `run.sh` (also behind `wsl.exe -e`/`--`), `Stop-Service`/`Restart-Service`/`sc.exe stop` with `actions.runner.*`, `systemctl stop 'actions.runner.*'` - is refused with the stop for THIS project's runner only (its `.ci-runner-win` processes, or `pkill -f '/srv/ci/runners/<slug>/'` in WSL), because a by-name stop also stops every other project's runner and its job. A pid-based stop and this project's exact service name pass; `wsl --shutdown`/`--terminate` is advised against, never refused; a quoted string that only contains a runner name is data.

## `Test-Completion-Check`

**Runs:** post-task (Stop, SubagentStop).

Pairing, logical retirement and audit use invocation-local ordered indexes, preserving exact identity/time/ownership predicates and deadlines. An unpairable controlled legacy observation can honor only its existing exact raw-pinned audited recovery; this is historical accounting, never pairing or fresh proof. Missing/foreign/uncontrolled/tampered originals stay UNKNOWN. Complete audits retain same-byte hashes and concurrent-change refusal. See [bounded historical processing](TEST-HOOK-RECOVERY.md#bounded-historical-processing-and-audited-observation-accounting).

Completed-failure delivery is reserved by raw evidence snapshot and project/client/session/agent, not task or diagnostic text. First report is advisory, exit 0; unchanged repeats are silent, explicitly unresolved in retained evidence, never Stop `additionalContext` or successful evidence. A/B/A suppression is retained. Malformed/unknown/capacity failures do not establish success or a default block; verified live/leaked processes remain a separate safety condition. See [repeat delivery](TEST-HOOK-RECOVERY.md#completed-failure-repeat-delivery).

An explicit audited `obsolete`/`cancelled` disposition can end repetition of one fully identified, noncurrent historical failed operation after verified resource retirement/cancellation and exact human approval. An immutable `identityKind: "legacy-missing"` request is the sole exception for the exact original empty-string fingerprint/absent repositoryState/twelve-hex root-key shape, with original command/end pins. Default recorded admission and exact-human-hash authorization stay strict; historical identity is never reconstructed. It records separate original/request/evidence hash pins, never recovery, PASS or current test evidence. Changed pins, a return to the original repository context, unknown identity and distinct current failures remain unresolved evidence, advisory by default; only verified active/leaking work retains a safety block. Both PowerShell hosts use the same serialized ledger; final byte pins are read after repository acquisition to detect changes during that wait. See [historical disposition](TEST-HOOK-RECOVERY.md#audited-obsolete-or-cancelled-history).

Explicit `-ResolveIncident` validates every retained original for a grouped incident (maximum 50), pins each run ID/SHA-256 and requires a separate clean recovery after all originals. Later or modified same-key failures do not inherit it; legacy singular associations stay compatible. Events, timeouts, settings, installer and menu behavior are unchanged. See [recovery contract](TEST-HOOK-RECOVERY.md).

Unpaired-observation diagnostics group result entries once per invocation by command fingerprint, preserving exact-run preference, path ordering and assigned-result exclusion. This avoids rescanning unrelated historical results for every observation when repository identity is unavailable. The index is messaging-only: no pairing, recovery, authorization or successful-state verdict is cached; the registered timeout and fail-closed evidence rules remain unchanged. Historical supersession rejects a different command before inspecting its outcome or leak list; same-command clean, nonterminated, leak-free and strictly-newer requirements are unchanged.

**Unavailable identity is not success:** legacy path-only observations remain unresolved when Git becomes readable. Identity diagnostics name runId, commandFingerprint, observedUtc, failedField and an exact supported recovery, not a generic rerun of a different scope. `-AuditEvidence -ProjectRoot <project> -AuditPath <new local JSON path>` exports original hashes and historical `UNKNOWN`/`SUPERSEDED` classification read-only; never `SUCCESS` or gate clearance. UNKNOWN does not establish success and does not create a default block. Audit `pairStatus=PAIRED|UNPAIRED` reports actual one-to-one assignment independently: paired rows carry their assigned result path/hash/outcome and no invented matching failure; pairing is not SUCCESS or CURRENT proof, and malformed active evidence prevents supersession. All historical receipt/observation originals remain byte-identical on disk, including valid Git-bound old records. Retirement filters only the current in-memory evaluation; age/state/supersession never authorizes deletion, fresh proof or a gate waiver. Actual failures/timeouts/leaks and live work remain independent. Evidence is reevaluated before atomic admission: unchanged findings are quiet, changed evidence is reconsidered. See [the audited procedure](TEST-HOOK-RECOVERY.md#unavailable-repository-state-and-audited-legacy-evidence).

A failed historical receipt can retain valid identity while the current repository is unavailable or different. Those cases report `repositoryState:unavailable` or `projectFingerprint:currentStateMismatch`; only missing/path-only recorded identity reports `projectFingerprint:unavailableOrLegacy`. All three still refuse CI recovery and preserve the actual failure.

**Recovery identity is not note eligibility.** An ordinary assertion failure keeps its recovery key and remains advisory while unresolved; a newer matching clean success creates no incident note. Termination (including `overall=error` with `terminated=true`), leaks, ownerless runs and explicitly enabled always-note mode remain eligible. New obligations carry a substantive cause and a project/command/run/outcome origin with receipt path and SHA-256; the snapshot remains independent of logical receipt retirement. Note prompts show at most five causes/origins plus the total count.

Legacy reconciliation runs under the existing project mutex before logical retirement. A byte-verified local backup is kept under `state/completion-backups` before changes. Only an empty-cause obligation uniquely matched to an exact-project ordinary failed receipt is retired, with evidence and backup recorded separately from resolved-run history. Uncorrelatable entries remain UNKNOWN, preserved and not resolved: a once-per-unchanged-state `systemMessage` reports at most five keys without requesting an invented lesson or continuing Stop. Evidence validation and repeat guards remain; nonsafety historical findings are advisory by default. Backups are local diagnostics; retain them until reconciliation is understood, never publish them.


The **after** stage of the three-stage test-health architecture is advisory by default, with a safety gate only for a verified live/leaked process in the current state, and it never runs a test, never spawns a process and never edits a file — its own state lives under `%LOCALAPPDATA%\HookMaker\state`, never in the project. The recursion guard comes first: `stop_hook_active` is deliberately NOT the guard: it is set for **any** gate's block, so exiting on it would make one gate silence the others. This gate stands down on **its own** block marker instead.

What that marker is keyed to changed with the task-identity work: a Stop event now belongs to the originating USER TASK - minted once at `UserPromptSubmit`, so a growing transcript, a retry, compaction or a client replaying a refusal as the next prompt is not a new request - and the admission ledger separates the semantic FINDING from the delivery. A gate therefore speaks once per task PER FINDING: the same unchanged complaint is not asked for a second time (it stays recorded as unresolved and the summary reports it), while evidence that actually changed carries a different fingerprint and is evaluated immediately. The ledger also retires what no session can continue: the chains, entries and unresolved rows of a session silent for 14 days are removed inside the same update lock (the current session is never touched), so a busy project no longer fills the 4,096-entry / 2 MB bound that turns every gate block into a refusal.

**A subagent is never blocked.** On `SubagentStop` a confirmed finding is delivered as a non-blocking advisory instead, because on Claude a Stop-family `decision:block` FORCES CONTINUATION: the reason becomes the subagent's next instruction, so it abandons the work it was dispatched to do and the parent receives this gate's text instead of the result. These conditions are task-level — guarded evidence for the whole task, which a subagent neither caused nor can clear — so blocking one would also break the rule that every block must name the action that clears it.

**Default safety gate, on the main agent's `Stop` only:** a guarded run whose recorded owner is verified alive, or a recorded leaked PID that is still verified alive. It blocks once per fingerprint and names the exact owned process to stop; SubagentStop remains advisory. Completed failures, termination/timeout history, missing or stale results, identity gaps and owed incident notes are advisory, exit 0, never successful evidence. Undeterminable state exits 0 silently.

Recovery still matches the complete argument vector: three suites do not supersede a one-suite failure. Same-command clean recovery or qualifying exact-SHA CI can settle historical evidence; `-ResolveIncident` remains an explicit, validated recovery route. Advisory delivery neither resolves the incident nor authorizes a duplicate local suite run.

**Staleness only weakens positive evidence, never negative findings:** a result older than the evidence window is not proof that a run happened for the current state (the "no result" case then applies), but an old hang is still an unrecorded hang, so the termination and leak cases are evaluated regardless of age until resolved. It **never** says "all tests passed": it reports only what the recorded evidence actually shows, and stays silent rather than claim a scope it has not seen. Every coordination file it consumes is **optional** — an absent file means that check is simply not evaluated, so a missing producer can never widen what this hook blocks on — and the per-run result/observed/active files are enumerated and aggregated across a project rather than read from one path (a legacy non-suffixed file from an older build is still honoured), so completion is accepted only when every current-state observed run is finished.

Logical retirement does not discard a later clean same-command result as historical supersession evidence. The complete retained result inventory is consulted only for result-level recovery; retired positives never re-enter current candidates or one-to-one observation assignment. Different-command, older, terminated or leaking results do not supersede a failure, and originals remain byte-identical.

A fully identity-matched, leak-free historical `ok` result still proves that its own observed run FINISHED, but is not fresh evidence. It no longer displaces a fresh paired success of another command on the same state; with only historical success, the advisory still reports `STALE`. Fresh success never hides a missing/mismatched/incomplete pair or an unresolved failure, timeout, termination or leak. One-to-one pairing and same-command-only supersession are unchanged, as is the 180-minute default evidence window. This applies to both Claude and Codex.

**`Test-Temp-Cleanup` race:** Stop hooks for one event run concurrently and independently, and registration order is display-only, never an execution order; when `Test-Temp-Cleanup` is installed for this project but has not yet recorded a result for the current fingerprint, this hook waits at most the coordination window and then **defers once** — it stays silent and re-evaluates on the next event, never retrying inside one invocation. `.env`: `TEST_COMPLETION_EVIDENCE_MINUTES` (how long a guarded result stays current for the same project state), `TEST_COMPLETION_ADVISORY_ONLY` (also demotes the live-process safety path; an invalid value falls back to advisory; historical findings are advisory regardless), `TEST_COMPLETION_ALWAYS_REQUIRE_NOTE` (require the durable `.ai/` note after any guarded run, not only after a hang/timeout/kill/slow run) and `TEST_COMPLETION_COORDINATION_WAIT_SECONDS` (the one-shot deferral wait, never a retry loop).

See [test-hook identity and recovery](TEST-HOOK-RECOVERY.md) for explicit user activation, literal argument identity and validated historical incident recovery. An observed run that has no paired result - a guarded run typed by hand without the full identity, or one killed before it wrote a result - is cleared by a **later** run (observed after it, so two runs started together stay separate) of the same command for the same current state that is paired to its own observation, finished `ok` and leaked nothing; a failed, leaking, older, unpaired or different-command run never clears it, so the printed recovery (re-run through the guarded runner) actually recovers.

A separate **possible-orphan advisory** rides the silent paths only: at Stop it lists processes whose image name matches `TEST_COMPLETION_SURVIVOR_PATTERNS` AND whose start time is later than this session's SessionStart baseline, printing pid, start time and a truncated command line, with the instruction to run the survivor sweep. It exists because this hook only ever sees GUARDED runs - anything started outside the guarded runner is invisible to it, and those are exactly the survivors that get left behind.

It is **advisory only and structurally cannot pre-empt a gate**: `Write-Finding` exits the script, so every blocking path returns before the advisory is reached. It never terminates a process, never reads process memory or environment, proves no ownership (which is why it only advises), enumerates once with a capped row count, fails open with an honest partial note, and is fingerprinted per session so an unchanged list is reported once. Two rules keep that promise real, both learned from a measured 13-Stop repeat loop that a client ended by overriding the hook: it stays **silent inside a continuation** (`stop_hook_active`), because Stop `additionalContext` continues the conversation; passive `systemMessage` and fingerprint suppression avoid repeating that loop; and it excludes **the client's own cohort** - this hook's ancestors and their DIRECT children, which is what the other Stop hooks of the same dispatch, the MCP servers and the tool shell are - whose pids are new on every event and used to churn the fingerprint into repeating.

One hop is the whole distinction: a deeper descendant, such as a test started through the tool shell, is the task's and is still reported. The durable-note obligation is keyed to the FINDING, never to the receipt that carried it: identity comes from the command the run executed plus how it ended, so repeated evidence of one defect owes ONE tagged note instead of one per receipt - a single repair in this project had minted four incident ids while seventy-four receipts sat on disk, each demanding its own.

A different command, or a different failure mode, still earns its own obligation, and an incident resolved under the previous scheme stays resolved. The `-ResolveIncident` command a failed run prints can now actually be run. Recovery used to demand that the incident key also be present in the durable-note ledger, and a plain assertion failure registers nothing there - only a termination or a leak does, because the lesson of a hang outlives the run that hung - so the escape hatch was refused on arrival, and a failure whose command no longer exists (a withdrawn TDD red, which the supersede matches by command and therefore never clears) had no exit at all.

The receipt recovery already found is what proves the incident; a note is required only where one is genuinely owed, and a termination is still held to its tagged note. Recovery's refusals now name the single field that is absent instead of three at once, the `projectFingerprint` case being the common one: the guarded runner persists whatever `-ProjectFingerprint` it was handed, and a hand-typed invocation hands it none. A run that completed but FAILED is also cleared by a green CI result for the exact commit HEAD is on, so a project whose heavy pass runs in CI is no longer told to run the same suite again locally.

Two hooks used to issue instructions that could not both be followed: the guard says not to run here a suite CI runs, and this gate then refused to finish until a clean run existed here. One measured task paid 345s and 310s of duplicate local running for it. The clearance is narrow on purpose - the working tree must be clean, because a CI result describes committed code only; the observation must name the current commit and must be newer than the failure it excuses; and a result that is red, pending, absent or unreadable changes nothing.

A run that was TERMINATED or that LEAKED a process keeps blocking whatever CI says, and still owes its tagged note: those are facts about this machine that no CI result speaks to. The notice names the commit it accepted, so the claim can be checked rather than trusted.

An unresolved negative result without a project fingerprint (the legacy shape) is retained regardless of age; age never forgives UNKNOWN or a failed run. Verified same-command recovery still accounts for the failure without rewriting its original; a Test-Temp-Cleanup installed in the user profile (global scope) is recognised for the cleanup-evidence coordination just like a project-scope one; and an incident ledger that cannot be written is reported as a non-blocking note instead of being swallowed.

**Another project's CI runner (2026-09-30).** A survivor candidate whose bounded ancestor walk reaches a `Runner.Listener`/`Runner.Worker` whose executable lies outside this project is left out of the advisory and counted as "another project's CI runner job - not this task's; do not terminate them"; a job under this project's own `.ci-runner-win` stays listed.

Expected-negative runner fixtures remain failed child outcomes, not product failures exempted by exit code. The enclosing Guard suite isolates its nested state and restores the caller environment; old polluted receipts require explicit audited verification and association, never deletion or SUCCESS rewriting. See [fixture recovery](TEST-HOOK-RECOVERY.md#expected-negative-test-fixtures).

## `Utf8-Encoding-Check`

**Runs:** pre-task (SessionStart) + post-task (Stop, SubagentStop) + native Git pre-push.

Complete opaque objects of 64–8192 bytes have one shared disk/Git evidence predicate: no UTF-8/UTF-16 BOM, at least 8 controls (below 32 except TAB/LF/CR), controls ≥1/16, high bytes ≥1/4, and strict UTF-8 plus both UTF-16 byte orders must all reject. Partial prefixes never qualify; helper/compiler failure preserves the original strict classifier. This narrow heuristic is not cryptographic validation or universal signature recognition; `.sig`/`.der` names grant no exemption. Original public binary acceptance is separate local input evidence; CI uses deterministic controls and real Git transport without redistributing third-party fixtures.

Detects strict-UTF-8 findings for text the task writes. SessionStart records a bounded metadata-only baseline (path/size/mtime/classification fingerprints, never contents). Stop inspects working-tree, staged and committed-during-task changes and reports new/changed invalid UTF-8 as advisory, exit 0, once per fingerprint. Partial/unknown state exits 0 silently and never establishes complete or clean coverage.

Strict decoder (never replacement-char decoding): UTF-8 with and without BOM both pass; UTF-16/UTF-32/Windows-1252/ANSI are non-UTF-8; a NUL-bearing binary is skipped as binary (bounded heuristic, never extension alone). Never rewrites, transcodes, normalizes line endings, or touches a BOM — it detects; the agent converts after review. Narrow documented exceptions live in an optional tracked `.utf8-encoding-exceptions.json` (exact path/pattern + encoding + concrete reason + verification; containment-checked, no `**/*`, malformed entries are rejected and grant nothing).

**Large text coverage (detection, not default block authority):** Filesystem, staged and outgoing text are validated with a stateful strict decoder, fixed 64 KiB byte chunks and a fixed character buffer; payloads are not accumulated across blobs. The default `UTF8_MAX_FILE_KB=65536` covers 64 MiB per text file/blob without an exception. Split multibyte sequences retain decoder state; incomplete final sequences fail. BOM precedence and the 8 KiB heuristic window remain. NUL parity classifies UTF-16/binary only at a density of at least 1/16 of that window; sparse literal NULs instead require complete strict UTF-8 validation, including the final decoder flush. Sparse prefixes over the cap remain unknown; invalid tails still fail. Git C/octal-quoted UTF-8 filenames are decoded as bytes before exact exception matching; malformed escapes or invalid pathname bytes never manufacture another identity. Explicit `.env` values survive the official updater byte-for-byte, including an old 1024 KiB cap: deliberately remove/change that key to adopt the new default. Above a configured cap, text remains unknown: native pre-push still exits 0, but it names the UNKNOWN coverage and the cap rather than returning silently, so an unreadable blob is never reported as clean; no encoding exception or advisory bypass is needed for valid in-cap catalogs. The exception JSON registry retains its separate bounded 1 MiB materialization limit.

Raw Git batches use a compiled .NET fixed-buffer adapter (shipped C# source, compiled by the existing PowerShell runtime; no separate dependency) and at most 32 pending requests. One dedicated worker performs synchronous raw pipe reads/writes/flushes, avoiding per-buffer thread-pool scheduling and per-window PowerShell overhead. The caller retains the deadline, kills the owned Git child on failure, cancels pending synchronous I/O and requires worker acknowledgment before disposing streams; failed worker cleanup is reported as `worker-cleanup`, never clean coverage. Responses require the requested object identity, blob type, nonnegative size, exact body length, final LF and terminal EOF. Reader initialization, missing objects, framing, short body, delimiter, trailing output, process exit and deadline failures have sanitized distinct diagnostics; transport failures are not fixed by resaving files or adding encoding exceptions. Malformed/truncated frames and read-deadline exhaustion refuse required coverage. The owned Git child is always reaped; the batch read is bounded by 20 seconds or the remaining registered hook deadline, whichever is shorter. Existing scan time/file/directory limits and lifecycle output/event contracts remain in force.

As the third native pre-push stage it validates the exact outgoing text blobs (new branches, multiple refs, deletions, force-pushes; even files later deleted) and reports confirmed invalid text as advisory, exit 0 by default; incomplete state stays silent, never clean. It reads every blob the push actually sends, in one batch pass with no file-count ceiling (`UTF8_MAX_FILES` bounds only the SessionStart/Stop scans), and skips content the remote already has - so a history rewrite that keeps every file's content scans nothing new.

## `Docs-Freshness-Check`

**Runs:** pre-task (SessionStart) + before `git push` (PreToolUse) + post-task (Stop).

**Before push.** PreToolUse recognizes shell `git push`, `git -C <dir> push` and pushes chained after `&&`, `;` or a newline. Confirmed non-doc impact without acknowledgment receives one advisory per fingerprint and exits 0 by default; documentation-only outgoing commits stay silent. Stop may request the same review, but never turns tested-parent evidence into final-SHA success: the new SHA stays UNTESTED until its own evidence exists. Committing reviewed docs preserves the acknowledgment because HEAD is not part of the impact fingerprint. Nested shell strings such as `bash -lc "git push"` are not reparsed. Existing SessionStart+Stop installs migrate through event-binding v10 in "Update previously installed hooks".

A detector/advisory for tracked public documentation affected by this task, never a prose rewriter: the agent reviews and edits. SessionStart records a metadata-only baseline (starting HEAD, repo-state fingerprint and tracked public `.md`/`.txt` hashes). Stop compares commits, staged and working-tree changes, excludes comment/blank-only noise and reports confirmed impact once per fingerprint with a bounded ranked candidate list. Missing acknowledgment at PreToolUse or Stop is advisory, exit 0 by default; undeterminable state exits 0 silently.

Hard exclusions (never requested for review regardless of config): `.ai`/`.claude`/`.codex`/`.agents`/`.cross-project-sync`, `secrets.md`, generated/vendor/build/cache directories, fixture/snapshot/golden files, and `LICENSE*`/`NOTICE*`/`COPYING*`. The impact fingerprint is content-hashed from only the non-doc changed files, so an unrelated documentation edit never shifts it. A fingerprint-bound acknowledgment records the review and clears its reminder; it is not required to permit completion or push by default. Use (`-Acknowledge -ProjectRoot <path> -ImpactFingerprint <fp> -Result Updated\|NoUpdate -Files <relative,doc,paths> -Reason "<concrete reason>"`): `Updated` requires at least one real, tracked/staged, in-project, non-excluded `.md`/`.txt` file; `NoUpdate` requires a concrete, non-generic reason (`none`/`n/a`/`done`/... are rejected).

Acknowledgement is local-only state, never committed, and a later non-doc change invalidates it, requiring a fresh review.
