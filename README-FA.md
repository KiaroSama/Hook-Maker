# راهنمای Hook Maker

ابزار ساخت، نصب و مدیریت هوک‌های Claude Code و Codex — به‌همراه هوک آماده‌ی همگام‌سازی دانش بین‌پروژه‌ای. هیچ مسیر پروژه‌ای داخل اسکریپت ثابت نشده است. تمام مسیرها، ارتباط‌ها، رویدادها و قوانین از فایل `sync-hooks.json` خوانده می‌شوند. فایل اصلی فقط یک نمونه غیرفعال و عمومی دارد و هیچ مسیر شخصی در آن ثبت نشده است.

## ساختار پوشه‌ها

| مسیر | نقش |
| --- | --- |
| `run.ps1` | لانچر — تنها اسکریپت ریشه؛ ویزارد را در همان ترمینال فعلی اجرا می‌کند (اول PowerShell 7) |
| `sync-hooks.example.json` | کانفیگ نمونه (داخل گیت — همین را CI اعتبارسنجی می‌کند) |
| `sync-hooks.json` | کانفیگ واقعی مسیریابی تو — **محلی و git-ignored** (مسیرهای پروژه‌های خودت داخلش است)؛ اولین اجرای ویزارد خودکار از نمونه ساخته می‌شود |
| `hooks\<Name>\` | برای هر هوک یک پوشه: `<Name>.ps1` + `.env.example` (در گیت) + `.env` (نسخه‌ی محلی تو، git-ignored) |
| `hooks\_hooklib.ps1` | هِلپرهای مشترک (stdin/`.env`/hash/JSON) که هوک‌های آماده dot-source می‌کنند؛ پیشوند `_` آن را از لیست انتخاب هوک بیرون نگه می‌دارد. همچنین در همان لحظه‌ی dot-source، ورودی/خروجی خودِ هوک را روی **UTF-8** تثبیت می‌کند: در غیر این صورت `[Console]` با code page کنسول رمزگشایی می‌کند و هوکی که کنسول متصل ندارد (کلاینت گرافیکی، یا هر والدی که آن را با `CreateNoWindow` و لوله‌های redirect اجرا کند) به code page پیش‌فرض OEM سیستم برمی‌گردد — که هر prompt، مسیر و نام فایلِ غیر‌ASCII را پیش از رسیدن به هوک خراب می‌کند. همچنین `Get-HookClientId` را در خود دارد — تنها جای مشترکی که تصمیم گرفته می‌شود **کدام کلاینت این هوک را اجرا می‌کند**: یک شناسه‌ی صریحِ کلاینت همیشه برنده است؛ شناسه‌ی صریحی که کلاینت شناخته‌شده نباشد به‌جای حدس‌زدن `unknown` می‌شود؛ `CLAUDE_PROJECT_DIR` سیگنال مثبت خودِ Claude است؛ و Codex فقط برای رانتایمی که هیچ شناسه‌ی صریحی ندارد پیش‌فرض می‌ماند — یعنی هر نصب Claude/Codex که پیش از وجود این تابع انجام شده، پس آن‌ها بایت‌به‌بایت مثل قبل resolve می‌شوند. فهرست شناسه‌های کلاینت اینجا عمداً تکرار شده است: رانتایم نصب‌شده خوداتکاست، پس نصاب همین فایل را داخلش بازنویسی می‌کند ولی هیچ فایل همسایه‌ای از `scripts\` کپی نمی‌کند و فهرست را نمی‌شود با dot-source به اشتراک گذاشت — در عوض `Test-ContextHooks.ps1` یکسان‌بودن این دو نسخه را assert می‌کند |
| `scripts\` | ویزارد، نصاب، اعتبارسنج و سوییت‌های تست (موتور، هوک‌های گیت‌هاب، RulesCheck، ویزارد، SecretsCheck، IgnoreRulesCheck، AiMemoryLoad/GraphReadCheck، AiMemoryCheck، ContextHooks، InstallRegistry) |
| `scripts\_clientcapability.ps1` | **تنها** توصیف canonical هر کلاینتی که Hook Maker برایش نصب می‌کند: مجموعه‌ی کلاینت‌ها، واژگان رویدادهای منطقیِ خودِ Hook Maker، اینکه هر کلاینت کدام‌یک از آن رویدادها را پشتیبانی می‌کند، و اینکه روی کدام‌یک واقعاً می‌تواند *block* کند. ویزارد و `Install-Hook.ps1` (و همچنین `_installlib.ps1`) هر دو از همین فایل مشتق می‌شوند و این یک نقص واقعی را برمی‌دارد: قبلاً دو فهرست رویدادِ مستقل وجود داشت — ویزارد ۱۲ رویداد پیشنهاد می‌داد و نصاب ۹ را می‌پذیرفت — پس `PermissionRequest`، `PostCompact` و `SubagentStart` هر سه از مسیر رویداد دلخواه در UI قابل انتخاب بودند و در نصب fatal می‌شدند. هر سه رویدادِ واقعی و مستندِ فعلی‌اند، پس فهرست ۹تایی سمتِ قدیمیِ آن جفت بود. تطبیق نام رویداد به بزرگی/کوچکی حرف حساس نیست، ولی همیشه املای canonical نوشته می‌شود، چون کانفیگ کلاینت‌ها روی نام trigger حساس است. یک نسخه‌ی دوم از این داده‌ها یک نقص است، نه بهینه‌سازی |
| `logs\` | لاگ اجراهای ویزارد (خودکار ساخته می‌شود، commit نمی‌شود) |
| `state\` | **محلی و git-ignored.** فایل `install-registry.json` — اینکه Hook Maker چه چیزی و کجا نصب کرده (بخش «به‌روزرسانی هوک‌های قبلاً نصب‌شده» را ببین)؛ هرگز مقدار سکرت/`.env`/prompt را نگه نمی‌دارد. |

## هوک‌های آماده

| هوک | زمان اجرا | کار |
| --- | --- | --- |
| `Cross-Project-.ai-Knowledge-Sync` | قبل از تسک | موتور سینک: دانش `.ai` تغییرکرده‌ی پروژه‌های مرتبط را برای بازبینی می‌آورد |
| `Git-Sync-Check` | قبل + بعد از تسک (Stop, SubagentStop) | در SessionStart/UserPromptSubmit وضعیت ناسینک را فقط به‌عنوان context غیرمسدودکننده گزارش می‌دهد (مخزن را تغییر نمی‌دهد)؛ در SessionStart همچنین یک baseline سانیتایز‌شده از worktreeها/شاخه‌های محلی مخزن را بی‌صدا ثبت می‌کند. در Stop/SubagentStop یک مرز تشخیص+دستور است، نه اجراکننده — خود هوک هرگز `git add`/`commit`/`pull`/`push`/`merge`/`rebase`/`branch -d`/`worktree remove` اجرا نمی‌کند؛ در عوض به عامل یک **دستور اجباری** می‌دهد که همین حالا مخزن را سینک کند (تغییرات تاییدشدهٔ همین تسک را stage، commit با پیام خنثی، و push)، و هر branch/worktree که در همین تسک ساخته یا تغییر داده را هم سینک کند (merge/push به مقصد مورد نظر؛ حذف worktree فقط وقتی کارش تمام شده)، بدون نیاز به یک درخواست جدا از کاربر — مگر این کار ناامن باشد (تست‌های شکست‌خورده، کار ناتمام، تغییرات نامرتبط قبلی، فایل‌های سکرت/محافظت‌شده، وضعیت merge/rebase/conflict، یا مانع دسترسی/مجوز)، که در این صورت کار را حفظ و دلیل را گزارش می‌کند. یک branch/worktree که پیش از این تسک بدون تغییر وجود داشته فقط context مشاوره‌ای است و هرگز مسدودکننده نیست؛ branchـی که push شده ولی هنوز merge نشده هم به‌تنهایی مسدودکننده نیست (این هوک هرگز فرض نمی‌کند هر branch ریموت باید merge شود). بازرسی واقعی گیت در **هر** Stop/SubagentStop اجرا می‌شود (هرگز صرفاً بر پایه زمان رد نمی‌شود؛ اسکن worktree/branch کران‌دار است و صادقانه تنزل می‌کند)؛ یک مسدودسازی واقعی برای هر دو کلاینت `decision:block` است، ولی یک مشاورهٔ غیرمسدودکننده (مثلاً یک worktree قفل‌شده/prunable) کلاینت‌آگاه است (`additionalContext` برای Claude، `systemMessage` برای Codex). تکرار خروجی با یک fingerprint از وضعیت actionable (شاخه/HEAD/upstream/ahead-behind/status به‌همراه یافته‌های task-scoped worktree/branch) و session id کنترل می‌شود، پس یک وضعیت مشخص فقط یک‌بار در هر session گزارش می‌شود، ولی وضعیت تغییریافته یا session جدید بلافاصله دوباره ارزیابی می‌شود |
| `Ai-Memory-Load` (در منو: `Ai-Context-Load`) | قبل از تسک | محتوای `.ai/memory.md` را به‌عنوان روتر شروع کار وارد context می‌کند و اسم همه‌ی فایل‌های دیگر `.ai/*.md` را هم نشان می‌دهد تا فایل مرتبط انتخاب شود، بدون بارگذاری بی‌دلیل بقیه. بر اساس محتوا و فهرست فایل‌ها fingerprint می‌شود؛ اگر `.ai/memory.md` نباشد ساکت است |
| `Ai-Memory-Check` (در منو: `Ai-Context-Check`) | بعد از تسک (Stop) | اگر context پروژه در `.ai/` قدیمی باشد، یادآوری می‌کند هرکدام از فایل‌های موجود `.ai/*.md` که به این تسک مربوط است به‌روز شود؛ اگر نکته‌ی ماندگاری ایجاد نشده، تمام می‌کند |
| `Graph-Read-Check` | قبل از تسک (SessionStart, UserPromptSubmit) | اگر `graphify-out/graph.json` وجود داشته باشد، در SessionStart یک‌بار سیاست کوتاه در دسترس بودن گراف را می‌دهد؛ در `UserPromptSubmit` **فقط وقتی prompt واقعاً نشان‌دهنده‌ی نیاز به فهم ساختار/وابستگی/call-path/معماری کدبیس باشد** — به **انگلیسی یا فارسی** (معماری/ساختار/وابستگی/مسیر فراخوانی/ماژول/نقطه ورود/بازنویسی/کل کدبیس …) — دوباره یادآوری می‌کند (fingerprint بر پایهٔ session + نسخهٔ گراف، پس تکراری نمی‌شود). اگر گرافی **نباشد** ولی تسک واقعاً به فهم کل کدبیس نیاز داشته باشد، ساختن گراف را پیشنهاد می‌دهد (یک بررسیِ در-دسترس-بودنِ کران‌دار و بدون-اجرای `graphify`، سپس create-then-query) یا اگر Graphify نباشد یک بار fallback به بازرسیِ هدفمندِ سورس؛ برای docs/config/اصلاح محلی ساکت می‌ماند. فقط detector/advisory است و هرگز Graphify یا کد پروژه را اجرا نمی‌کند |
| `Graph-Update-Check` | بعد از تسک (Stop) | اگر `graphify-out/graph.json` قدیمی باشد، تصمیم `graphify update .` را بر اساس **تاثیر ساختاری** (نماد/export/import/رابطه‌ی فراخوانی یا ارث‌بری اضافه/حذف/تغییرنام‌شده، نقطه‌ی ورود جدید، وابستگی بین‌فایلی تغییریافته) به خود هوش مصنوعی می‌سپارد — هرگز بر اساس تعداد فایل تغییریافته: یک تغییر تک‌فایلی می‌تواند همچنان مرتبط با گراف باشد، در حالی که یک تغییر چندفایلی (فقط مستندات/کامنت/فرمت، مقدار literal/config، خروجی تولیدشده) می‌تواند بی‌ربط به گراف باشد |
| `Cloudflare-Deploy` | بعد از تسک (Stop) | در پروژه‌های Worker (وجود wrangler config)، اول **آمادگی release** را چک می‌کند — یک گیت قطعی، هرگز بر پایه‌ی ترتیب ثبت/منو (چون هوک‌های هم‌رویداد می‌توانند هم‌زمان اجرا شوند): تا زمانی که working tree تمیز نباشد، کامیت دقیق push‌شده (به هر upstream، نه فقط گیت‌هاب) شناخته نشود، CI (اگر `.github/workflows` دارد) برای همان SHA سبزِ تاییدشده نباشد، و — اگر `Test-Temp-Cleanup` روی این پروژه نصب باشد — نتیجه‌ی **تازه‌ی `clean`** برای وضعیت فعلی ثبت نکرده باشد، کاملاً ساکت می‌ماند (نه اینکه فقط یادآوری را رد کند؛ اگر روی همان Stop مسابقه‌ای رخ دهد، Stop بعدی دوباره ارزیابی می‌کند، هرگز لوپ). `clean` تنها دسته‌ی آماده‌ی release است: `review-required`، `residue-confirmed`، `partial` و `unknown` همه این هوک را ساکت نگه می‌دارند، و همین‌طور یک fingerprint قدیمی، نبودِ رکورد، و هر مقداری که این نسخه نمی‌شناسد. پیامد عملیِ الزامِ `clean` را در نظر بگیر: پروژه‌ای که همیشه یک artifact بازبینیِ untracked دارد — مثلاً پوشه‌ی `coverage/` — نتیجه‌اش `review-required` است، پس این هوک اکنون ساکت می‌ماند در جایی که نسخه‌ی قبلی پیشنهاد دیپلوی می‌داد. وقتی آماده بود، هوش مصنوعی را از یک **تصمیم شایستگی دیپلوی** عبور می‌دهد (فقط وقتی دیپلوی کن که تسک کامل است، تست/typecheck/lint/build پاس شده، کامیت دقیق release مشخص است، اگر CI دارد سبز است، فایل سکرت/محلی، تغییر نامرتبط یا باقیمانده‌ی cache/temp تست اضافه نشده، محیط/binding/migration فهمیده شده و قوانین پروژه اجازه می‌دهند — وگرنه بدون دیپلوی تمام کن)، **انتخاب صریح محیط** (هرگز پیش‌فرض بی‌صدا روی production نمی‌رود)، یک **بازبینی شرطی مخصوص Cloudflare پیش از دیپلوی** (اسم Worker، متغیرهای محیطی، bindingها، D1/KV/R2/Queues/Durable Objects + migration، service binding، route، cron، compat flags، نسخه‌ی CLI، خروجی build — فقط آنچه به این تغییر مربوط است)، و **تایید اجباری بعد از دیپلوی** (ثبت محیط/Worker/SHA دقیق/دستور دیپلوی بدون سکرت/نسخه یا URL، سپس smoke-test یا تایید دیگر — خروج کد صفر به‌تنهایی هرگز دلیل کافی نیست، و شکست هرگز پنهان یا کورکورانه دوباره دیپلوی نمی‌شود) |
| `Skills-Check` | قبل از تسک (SessionStart, UserPromptSubmit) + بعد از تسک (Stop) | در SessionStart اسکیل‌های موجود پروژه + سیاست را یک‌بار در هر session نشان می‌دهد. در `UserPromptSubmit` یادآوری می‌کند فقط اسکیلی که به این تسک مربوط است انتخاب شود (fingerprint‌شده، پس در یک session تکراری نمی‌شود). در `Stop` الزام می‌کند سامری نهایی خط `Skills used: <name1>, <name2>` را برای اسکیل‌هایی که **واقعاً استفاده شده‌اند** بیاورد — هرگز اسکیلی که فقط نصب/موجود/کشف/کپی/بررسی‌شده ولی استفاده‌نشده؛ اگر هیچ اسکیلی استفاده نشده، این خط کلاً حذف می‌شود؛ هرگز برای تسک ساده اسکیل تحمیل نمی‌کند |
| `Mcp-Usage-Check` | قبل از تسک (SessionStart, UserPromptSubmit) | در SessionStart سیاست فشرده‌ی MCP را یک‌بار می‌دهد. در `UserPromptSubmit` **فقط وقتی prompt نشان‌دهنده‌ی نیاز واقعی به داکیومنت/مرورگر/دیتابیس/گیت‌هاب/سایر MCPها باشد** دوباره یادآوری می‌کند (fingerprint per-session) — برای promptهای بدون این نشانه ساکت می‌ماند |

هوک‌های lifecycle منطبق با یک Event هم‌زمان اجرا می‌شوند و به هم وابسته نیستند؛ ترتیب ثبت (و جایگاه در منو) فقط نمایشی است و هرگز ترتیب اجرا را تضمین نمی‌کند. `Cloudflare-Deploy` و `Test-Temp-Cleanup` به‌جای فرض «بعد از هم» اجرا شدن، وضعیت را از طریق یک فایل fingerprint‌شده‌ی کوچک رد و بدل می‌کنند. تنها ترتیب قطعی، زنجیره بومی pre-push است.
این زنجیره مسیر واقعی `core.hooksPath` را برای حالت پیش‌فرض، نسبی، تو‌در‌تو، مطلق و مسیر دارای فاصله رعایت می‌کند؛ هوک قبلی را فقط یک‌بار حفظ می‌کند و نصب مجدد idempotent است.

## کانفیگ هوک‌ها (.env)

هر پوشه‌ی هوک یک `.env.example` (داخل گیت) دارد. آن را به `.env` کپی کن (git-ignored) و مقادیر محلی‌ات را بنویس — مهم‌تر از همه `TARGET_PROJECTS` (مسیر پروژه‌ها با جداکننده‌ی `;`)، `EVENTS` و `CLIENTS` (`Both`، `Claude` یا `Codex`). بعد از منو `۱ ← ۳` (نصب از کانفیگ) استفاده کن: هوک **بدون هیچ سوالی** در همه‌ی پروژه‌های لیست نصب می‌شود. فایل `.env` موتور سینک هم کلید `SYNC_PROJECTS` دارد که گزینه‌ی ۱ منو پیشنهاد می‌دهد به‌جای تایپ مسیرها از آن استفاده شود.

## منوی تعاملی و لانچر (روش پیشنهادی)

`run.ps1` را اجرا کن. اگر بیرون از Windows Terminal باشی و `wt.exe` نصب باشد، ویزارد در یک پنجره‌ی Windows Terminal باز می‌شود؛ وگرنه در همان کنسول با pwsh (یا PowerShell 5) اجرا می‌شود.

گزینه‌های منوی اصلی:

1. **ساخت یا نصب هوک** — چهار زیرگزینه دارد:
   - **ساخت هوک جدید (با قالب آماده):** اسم هوک را بده، یکی از پنج قالب را انتخاب کن، حداکثر یک سوال جواب بده و یک هوک کامل و کارا در `hooks\` ساخته می‌شود (و در صورت تایید همان‌جا نصب می‌شود):
     1. **Context note** — یک یادداشت ثابت (متنی که خودت می‌دهی) را در هر session/prompt به عامل تزریق می‌کند.
     2. **Prompt guard** — پیام‌هایی که کلمات ممنوعه (لیست خودت) دارند را بلاک می‌کند.
     3. **Tool logger** — هر فراخوانی ابزار را در یک فایل لاگ کنار هوک ثبت می‌کند.
     4. **Git sync check** — وقتی پروژه با ریموت گیتش سینک نیست هشدار می‌دهد (تغییرات commit نشده، کامیت‌های push/pull نشده، یا شاخه‌ی بدون upstream)؛ برای پروژه‌ی سینک یا غیر-گیت ساکت است و آفلاین با آخرین وضعیت مقایسه می‌کند.
     5. **Empty skeleton** — اسکلت کامنت‌گذاری‌شده برای منطق دلخواه خودت.
   - **نصب هوک موجود:** یک لیست نشان می‌دهد که گزینه‌ی ۱ آن **«انتخاب همه‌ی هوک‌ها»** است — یک عمل تجمیعی، نه خودِ یک هوک — که **گروه سینک و همه‌ی هوک‌های فردی زیر** را در یک اجرا نصب می‌کند. لازم نیست گزینه‌ی ۲ را هم جدا بنویسی — خودِ گزینه‌ی ۱ همیشه گروه سینک را هم شامل می‌شود. مجموعه‌ی هوک‌های فردی هر بار پویا از تعداد واقعی هوک‌های موجود ساخته می‌شود (نه یک عدد ثابت)، و گروه سینک همیشه دقیقاً یک‌بار اجرا می‌شود حتی اگر گزینه‌ی ۲ هم صریحاً در انتخاب باشد (مثل `1,2`). گزینه‌ی ۲ **«ساخت یا به‌روزرسانی گروه همگام‌سازی»** به‌تنهایی است و از گزینه‌ی ۳ به بعد هوک‌های `hooks\` می‌آیند — هر هوک با یک تگ زمان‌بندی رنگی و یک توضیح یک‌خطی؛ منو از پنج رنگ متمایز استفاده می‌کند تا تگ‌ها با هم قاطی نشوند: `[pre-task]` (نعنایی)، `[post-task]` (کهربایی)، `[pre+post-task]` (فیروزه‌ای)، تگ تجمیعی `[all]` (ارکیده)، و اکشن‌های `[manage]` (سبزآبی)؛ `Cloudflare-Deploy` همیشه **آخرین** هوک فردی در لیست است. می‌توانی **چندتا را با هم** با ترکیب لیست و بازه نصب کنی (مثل `3-8,20`): یا event پیشنهادی هر هوک را با کلاینت/پروژه‌های یکسان استفاده کنی، یا هرکدام را جدا تنظیم کنی؛ در پایان یک سامری دقیق نشان می‌دهد چه چیزی نصب می‌شود. ترکیب گزینه‌ی `1` با انتخاب‌های دیگر (مثل `1,5`) هرگز چیزی را دوبار نصب نمی‌کند. اگر مرحله‌ی گروه سینک لغو شود، هوک‌های فردی نصب نمی‌شوند و چیزی به‌دروغ «تکمیل‌شده» گزارش نمی‌شود. اگر فقط گزینه‌ی ۲ (بدون ۱) انتخاب شود، مثل قبل تنها گروه سینک اجرا می‌شود؛ اگر داخل یک انتخاب چندتایی هم باشد (مثل `2,4-6`)، اول ویزارد گروه سینک کامل اجرا می‌شود و بلافاصله بعدش بقیه‌ی هوک‌های انتخابی نصب می‌شوند — یک بار، بدون نیاز به برگشتن به این منو. **مسیرهای مشترک:** وقتی گروه سینک کنار هوک‌های دیگر اجرا شود (از جمله با گزینه‌ی `1`)، مسیرهای پروژه‌ای که برای گروه سینک وارد می‌کنی به‌عنوان مقصد نصب همه‌ی هوک‌های دیگر هم استفاده می‌شوند — یک بار وارد می‌کنی، نه یک بار برای هر هوک. خودِ موتور سینک در این لیست به‌عنوان یک هوک جداگانه دیده نمی‌شود — چون نصبش به‌صورت هوک دلخواه، `-Profile`/کانفیگ مسیریابی را نمی‌گیرد و کار نمی‌کند؛ فقط از همین مسیر (گزینه‌ی ۱ یا ۲) قابل نصب است. اگر گروه سینک اجرا شود، مسیر ریشه‌ی هر پروژه را یکی‌یکی وارد می‌کنی (`done` پایان، `undo` حذف آخرین، `0` بازگشت، `exit` خروج؛ حداقل دو پروژه؛ مسیر تکراری/ناموجود/تودرتو رد می‌شود) — این سوال‌های تکراری داخل یک سوال والد با شماره‌گذاری **سلسله‌مراتبی** نشان داده می‌شوند (مثل `12-1.`، `12-2.`، `12-3.`) نه اینکه هر کدام یک عدد جدید در سطح بالا بگیرند؛ ورودی نامعتبر/تکراری/تودرتو یا `undo` همان شماره را نگه می‌دارد یا یک قدم برمی‌گرداند. کلاینت را انتخاب می‌کنی و بعد از خلاصه با Enter (پیش‌فرض y) اجرا می‌شود. اگر **یک** هوک را انتخاب کنی، اولین گزینه‌ی رویداد همیشه رویدادهای پیشنهادیِ همان هوک است (مثلاً «رویدادهای پیشنهادی این هوک (Stop)») — یک Enter ساده آن را دقیقاً روی چیزی که آن هوک واقعاً لازم دارد نصب می‌کند، نه یک پیش‌فرض عمومی؛ گزینه‌های ثابت دیگر و یک لیست کاملاً دلخواه هم همچنان در دسترس‌اند.
   - **نصب از کانفیگ:** بدون سوال، از `.env` هر هوک (`EVENTS`/`TARGET_PROJECTS`/`CLIENTS`) نصب می‌کند.
   - **به‌روزرسانی هوک‌های قبلاً نصب‌شده:** آخرین زیرگزینه — نگاه کن به بخش «به‌روزرسانی هوک‌های قبلاً نصب‌شده» پایین‌تر.

   قالب ۴ همان `hooks\Git-Sync-Check.ps1` آماده هم هست. در ویزارد، `0` یک سوال به عقب برمی‌گردد و `exit` خارج می‌شود؛ منو دیگر برای Enter مکث نمی‌کند.
2. **نمایش profileهای موجود**
3. **اعتبارسنجی کانفیگ**

نکته‌های ویزارد:

- شناسه profile از هش مسیرهای مرتب‌شده ساخته می‌شود؛ اجرای دوباره با همان مسیرها همان profile را به‌روزرسانی می‌کند و وضعیت sync حفظ می‌شود.
- ویزارد پوشه `.ai` هر پروژه را در صورت نبودن می‌سازد؛ پوشه‌های `.claude` و `.codex` پروژه‌ها هم اگر نباشند خودکار ساخته می‌شوند.
- لاگ هر اجرا در پوشه `logs` با نام `Setup-SyncGroup_YYYY-MM-DD_HH-mm-ss_UTC.log` ذخیره می‌شود (سطح‌ها: DEBUG/INFO/WARNING/ERROR/CRITICAL، زمان UTC). همه ورودی‌های کاربر هم در لاگ ثبت می‌شوند.
- سوییچ `-NoInstall` فقط کانفیگ را می‌نویسد و نصب hook را انجام نمی‌دهد.

## هوک کجا نصب می‌شود — نصب خوداتکاست (بدون وابستگی به پوشه‌ی Hook Maker)

هر نصب، **رانتایم هوک را داخل خود مقصد کپی می‌کند** (شبیه هوک‌های `.kiro`): اسکریپت هوک، `_hooklib.ps1` مشترک، `.env` آن (اگر باشد) و — برای موتور سینک — یک کپی از کانفیگ مسیریابی:

- برای Claude در `<پروژه>\.claude\hooks\Hook-Maker\` (ثبت در `<پروژه>\.claude\settings.local.json` — خودکار git-ignore، چون دستور مسیر مطلق ماشین توست).
- برای Codex در `<پروژه>\.codex\hooks\Hook-Maker\` (ثبت در `<پروژه>\.codex\hooks.json`؛ فقط بعد از trust با `/hooks` بارگذاری می‌شود).

دستور ثبت‌شده به همان کپی داخل پروژه اشاره می‌کند؛ پس **جابه‌جایی، تغییر نام یا حذف پوشه‌ی Hook Maker هیچ هوک نصب‌شده‌ای را نمی‌شکند**. روی دیگر سکه: کپی‌ها خودکار به‌روز نمی‌شوند — بعد از تغییر یک هوک، `.env` آن یا گروه سینک، نصب (یا گروه سینک) را دوباره اجرا کن تا کپی‌ها تازه شوند؛ نصب مجدد ثبتِ قبلیِ همان هوک را **جایگزین** می‌کند (حتی ثبت قدیمی که به پوشه‌ی ابزار اشاره می‌کرد)، نه تکرار. محتوای دیگرِ فایل تنظیمات دست نمی‌خورد و قبل از نوشتن backup تاریخ‌دار ساخته می‌شود.

نصب سراسری هم همین‌طور است: `scripts\Install-Hook.ps1` بدون `-TargetProject` در `~\.claude\hooks\Hook-Maker\` و `~\.codex\hooks\Hook-Maker\` کپی و در `settings.json`/`hooks.json` سراسری ثبت می‌کند.

فهرست «هوک‌های موجود» شماره‌های **ثابت** دارد، پس سه گزینه‌ی مدیریتی هرگز با اضافه/ساختن هوک جابه‌جا نمی‌شوند:

| شماره | چیست |

| `2` | ساخت یا به‌روزرسانی گروه سینک |
| `3`–`23` | ۲۲ هوک آماده، با ترتیب پین‌شده (`9` همان `Docs-Freshness-Check` است؛ `20`–`22` سه هوک سلامتِ تست‌اند؛ `23` همان `Utf8-Encoding-Check` است) |

## به‌روزرسانی هوک‌های نصب‌شده (`24`)

چون نصب‌ها کپی خوداتکا هستند، ویرایش سورس یک هوک زیر `hooks\` (یا به‌روز کردن خودِ Hook Maker) هیچ کپی از قبل نصب‌شده را تغییر **نمی‌دهد** — کپی‌ها لحظه‌ی نصب فریز می‌شوند. به‌جای انتخاب و تنظیم دوباره‌ی تک‌تکِ هوک‌ها، از گزینه‌ی **`24` به‌روزرسانی هوک‌های نصب‌شده** استفاده کن (گزینه‌ی `4` در زیرمنوی «ساخت یا نصب هوک» هم نام مستعارِ سازگاری برای **همان** پیاده‌سازی است).

این گزینه یک رجیستری نصب محلی را می‌خواند، یک برنامه نشان می‌دهد، فقط **یک** تاییدیه می‌پرسد، و بعد هر چیزی که نیاز به ترمیم دارد را ترمیم می‌کند — با استفاده از همان رویدادها، انتخاب کلاینت، دامنه‌ی پروژه/سراسری و (برای موتور سینک) profile/کانفیگِ نصب اولیه، پس هیچ سوالی دوباره پرسیده نمی‌شود. به‌روزرسانی از **مسیر سورسِ ذخیره‌شده‌ی** هر رکورد انجام می‌شود، نه مسیری که از روی نام هوک بازسازی شده باشد؛ پس هوکی که خودت ساخته‌ای از همان‌جایی که واقعاً هست تازه می‌شود. اگر سورسی جابه‌جا یا حذف شده باشد، «گم‌شده» گزارش و رد می‌شود و هیچ مسیر دیگری حدس زده نمی‌شود. هرگز هوکی که قبلاً نصب نشده را نصب نمی‌کند، هرگز محتوای نامرتبطِ فایل تنظیمات را دست نمی‌زند، و یک اجرای دوم که چیزی تغییر نکرده باشد همه‌چیز را از‌قبل-به‌روز گزارش می‌کند.

## وضعیت هوک‌ها (`25`)

گزینه‌ی **`25`** مسیری را که انتخاب می‌کنی اسکن می‌کند، هر هوکِ نصب‌شده‌ای که پیدا کند گزارش می‌دهد — **چه مالِ Hook Maker باشد چه مالِ ابزار دیگری** — و نتایج تأییدشده را ثبت می‌کند. این یک عملیات صریح و درخواستی است: هنگام شروع هیچ اسکنی انجام نمی‌شود، و گزینه‌ی `24` همچنان فقط به رجیستری خودش نگاه می‌کند.

دو سؤال می‌پرسد:

۱. **`Root folder to scan`** — ریشه‌ی یک پروژه، پوشه‌ی والدِ چند پروژه، یک دایرکتوری `.claude` / `.codex` / `.git` / `hooks` / `Hook-Maker`، هر جدّ یک هوک نصب‌شده، یا ریشه‌ی درایو مثل `G:\`. مسیرهای داخل کوتیشن، مسیرهای دارای فاصله و متغیرهای محیطی همه کار می‌کنند و مسیر پیش از اسکن canonical می‌شود. لازم **نیست** ریشه‌ی دقیق پروژه را بدهی: با دادن `...\.claude\hooks\Hook-Maker` رو به بالا دنبال ثبت‌نامِ متناظر می‌گردد.
۲. **`Also inspect the current user's global Claude, Codex and Kiro hook locations?`** — پیش‌فرض **نه** است (Enter یعنی نه). جواب بله فقط مسیرهای متعارفِ سراسریِ `.claude`/`.codex` کاربر فعلی را بررسی می‌کند و هرگز کل پوشه‌ی خانگی را پیمایش نمی‌کند. جواب نه یعنی آن فایل‌ها **اصلاً باز نمی‌شوند**، از هیچ مسیر کدی.

چه چیزی را بررسی می‌کند: `settings.local.json` و `settings.json` مربوط به Claude، فایل `hooks.json` مربوط به Codex، درخت‌های رانتایمی که آن ثبت‌نام‌ها به آن اشاره می‌کنند، و هوک‌های بومی Git — شامل فایل‌های `.git` دارای `gitdir:` (worktree و submodule) و `core.hooksPath` سفارشی. همه‌ی رویدادها و handlerها پارس می‌شوند، نه فقط مالِ Hook Maker، و `*.sample` نادیده گرفته می‌شود.

**هیچ‌چیز هرگز اجرا نمی‌شود.** دستورهای پیداشده در تنظیمات فقط به‌عنوان متن پارس می‌شوند — نه اجرا، نه dot-source، نه حل‌شدن با مفسر — و هیچ هوک گیتی فراخوانی نمی‌شود. اسکن نسبت به پوشه‌ای که به آن اشاره می‌کنی فقط‌خواندنی است و هرگز چیزی داخلش نمی‌نویسد.

نقاط reparse (symlink، junction، mount point) **دنبال نمی‌شوند** و به‌عنوان رد‌شده گزارش می‌گردند. دایرکتوری‌هایی که خوانده نمی‌شوند **پوشش ناقص** می‌سازند، نه اسکنِ شکست‌خورده: یافته‌های تأییدشده همچنان ذخیره می‌شوند، اجرا partial گزارش می‌شود، و رکوردهای زیر نواحی ناخوانا هرگز «گم‌شده» علامت نمی‌خورند. اسکنی که همه‌جا را ندیده هرگز نمی‌تواند ادعا کند دیده است.

نتایج تأییدشده در `<Hook-Maker>\state\install-registry.json` ذخیره می‌شوند — همان رجیستری واحدِ نصب‌ها، با رکوردهای کشف‌شده جدا از رکوردهای مدیریت‌شده‌ی خودِ Hook Maker. اسکن بعدی همان رکورد را به‌روز می‌کند نه اینکه تکراری بسازد؛ دو هوک هم‌نام در مسیرهای متفاوت جدا می‌مانند. اسکن لغو‌شده یا شکست‌خورده هیچ‌چیز نمی‌نویسد.

یافته‌ها یا **فقط‌وضعیت** هستند یا **قابل‌حذفِ امن**. هر چیزِ مبهم، مشترک بین چند هوک، یا بیرون از ریشه‌ی شناخته‌شده‌ی هوک نمایش داده می‌شود ولی هرگز خودکار حذف نمی‌گردد.

## حذف نصبِ هوک‌های نصب‌شده (`26`)

گزینه‌ی **`26`** همه‌ی نصب‌های ردیابی‌شده را — مالِ خودِ Hook Maker به‌علاوه‌ی هر چیزی که گزینه‌ی `25` کشف کرده — فهرست می‌کند و آن‌هایی که انتخاب کنی را حذف می‌کند. همان نحو `1` / `1,2` / `1,2,3-6` را می‌پذیرد و نوع رکورد و امکان‌پذیر بودن حذف را برای هر ردیف نشان می‌دهد.

دو نوع ردیف ارائه می‌شود:

- **تکی** — یک ردیف برای هر نصب منطقی، با نمایش هوک (و profile برای موتور سینک)، دامنه، مسیر دقیق پروژه یا `global`، و کلاینت‌هایی که برایشان نصب شده.
- **تجمیعی** — بعد از آن‌ها، یک ردیف برای هر پروژه (`Remove all Hook Maker hooks from project: <path>`) و در صورت وجود نصب سراسری، `Remove all global Hook Maker hooks`.

انتخاب همزمانِ یک ردیف تجمیعی و یکی از ردیف‌های تکیِ خودش، هر نصب را دقیقاً یک‌بار حذف می‌کند (حذف تکراری بر اساس شناسه‌ی رکورد).

**فایل‌های سورس هوک‌های تو هرگز حذف نمی‌شوند.** حذف نصب فقط کپی‌های رانتایمِ نصب‌شده، ثبت‌نام‌های کلاینت، یکپارچه‌سازی native Git متعلق به همان رکورد، و خودِ رکورد رجیستری را برمی‌دارد. اصل فایل‌ها زیر `hooks\` دست‌نخورده می‌مانند، پس هر وقت خواستی می‌توانی دوباره نصب کنی.

ویژگی‌های ایمنی:

- مالکیت با **مسیرِ** رانتایم مدیریت‌شده اثبات می‌شود و در هر سه فیلد `command`، `commandWindows` و `command_windows` بررسی می‌گردد — هرگز با نام فایل. اگر handler خودت به اسکریپتی با نام مشابه در جای دیگری اشاره کند، حفظ می‌شود.
- فقط پوشه‌ی رانتایمِ همان رکورد و فقط داخل مرزی که فیزیکی تأیید شده حذف می‌شود. رانتایم هوک دیگر، ریشه‌ی مشترک `Hook-Maker` وقتی هوک دیگری باقی است، و هر مسیر بیرون از محدوده‌ی مورد انتظار، همگی رد می‌شوند.
- فایل‌های تنظیمات با همان قفل هر-فایل، نویسنده‌ی اتمیک و پشتیبان زمان‌دار نصب نوشته می‌شوند؛ گروه‌ها، handlerها و پراپرتی‌های JSON نامرتبط دست‌نخورده می‌مانند.
- قبل از هر تغییری، خلاصه‌ای از هر نصب، دامنه، کلاینت، مسیر رانتایم، مسیر تنظیمات و دخیل بودن native Git می‌بینی و فقط با `y` صریح ادامه می‌یابد. لغو، رد کردن، بازگشت، خروج یا انتخاب نامعتبر **هیچ** تغییری ایجاد نمی‌کند — نه پشتیبان، نه نوشتن رجیستری، نه حذف فایل.
- رکورد فقط بعد از تأیید موفقیت پاک‌سازیِ متعلق به خودش از رجیستری حذف می‌شود. اگر حذف نصب ناقص یا مبهم باشد، رکورد با وضعیت دقیقِ خطا/نیاز-به-ترمیم-دستی **نگه داشته** می‌شود، نه اینکه موفقیتی که رخ نداده گزارش شود. تکرار حذف نصب idempotent است.
- برای native Git، wrapper مدیریت‌شده حول مراحل باقی‌مانده بازتولید می‌شود، یا اگر هیچ مرحله‌ی مدیریت‌شده‌ای نماند، هوک `pre-push` قبلیِ حفظ‌شده‌ات **بایت‌به‌بایت** برگردانده می‌شود. wrapperای که دستکاری شده یا drift کرده حفظ و برای ترمیم دستی گزارش می‌شود، نه بازنویسی.

مثل نصب، اینجا هم «rollback جبرانی» استفاده می‌شود (پوشه‌های رانتایم کنار گذاشته و در صورت شکست مرحله‌ی بعد برگردانده می‌شوند)، **نه** اتمیک‌بودن در برابر کرش ماشین — بخش «محدودیت‌های شناخته‌شده» را ببین.

### «به‌روز است» دقیقاً یعنی چه

یک نصب فقط وقتی **به‌روز** گزارش می‌شود که همه‌ی این شرط‌ها برقرار باشند — و هرگز صرفاً از روی هش‌های ذخیره‌شده‌ی رجیستری نتیجه‌گیری نمی‌شود، چون آن‌ها فقط وضعیتِ لحظه‌ی نصب را توصیف می‌کنند:

- رکورد و schema رجیستری معتبر باشد و سورس ثبت‌شده هنوز پیدا شود؛
- **مانیفستِ فایل‌های مدیریت‌شده‌ی سورس** با آنچه هنگام نصب ثبت شده یکی باشد؛
- هر فایل مدیریت‌شده‌ای که **واقعاً روی دیسک است** با همان مانیفست بخواند؛
- هر ثبت‌نام موردانتظار **دقیقاً یک بار** وجود داشته باشد، با رویداد/matcher/دستور/timeout درست همان کلاینت؛
- هیچ ثبت‌نام کهنه‌ای از همان نصب روی رویداد دیگری باقی نمانده باشد؛
- مقصد/دامنه/profile/کانفیگ هنوز موجود و معتبر باشند؛
- یکپارچگی زنجیره‌ی pre-push بومی (در صورت وجود) سالم باشد.

هر چیز دیگری با یک دلیل دقیق برای **به‌روزرسانی** برنامه‌ریزی می‌شود (تغییر سورس، فایل نصب‌شده‌ی گم‌شده، فایل نصب‌شده‌ی تغییریافته، رانتایم مشترکِ کهنه، ثبت‌نام گم‌شده، ثبت‌نامِ منحرف‌شده، ثبت‌نام تکراری، ثبت‌نام کهنه، یکپارچگی بومیِ کهنه)، یا با یک دلیل دقیق و بدون تخریب **رد** می‌شود. بنابراین حذف، خراب‌کردن یا دست‌کاری دستیِ یک فایل رانتایمِ نصب‌شده — یا حذف/تغییر یک ثبت‌نام — حتی وقتی سورس اصلاً عوض نشده باشد هم تشخیص داده و ترمیم می‌شود.

### فایل‌های مدیریت‌شده

مانیفست **همه‌ی** فایل‌هایی را پوشش می‌دهد که نصاب برای آن هوک کپی می‌کند: اسکریپت اصلی، `_hooklib.ps1` مشترک، فایل `.env` خودِ هوک (به‌صورت هشِ کل فایل — مقادیرش هرگز خوانده یا ذخیره نمی‌شوند)، هر فایل کمکی/داده‌ی دیگر در پوشه‌ی سورس هوک، و کانفیگ کپی‌شده‌ی موتور سینک. پس تغییر فقط در `.env` یک هوک یا فقط در یک فایل کمکیِ کپی‌شده هم باعث به‌روزرسانی می‌شود. فایل‌هایی که نصاب کپی نمی‌کند (`.env.example`) و فایل‌هایی که در زمان اجرا ساخته یا تغییر می‌کنند (`SYNC-PROJECTS.txt`، لاگ‌ها) عمداً کنار گذاشته شده‌اند تا هرگز باعث انحرافِ کاذبِ دائمی نشوند.

### معنای مستقل برای هر کلاینت

Claude، Codex و Kiro **جداگانه** داخل یک نصب منطقی ردیابی می‌شوند. نصب یک هوک برای Claude روی `SessionStart` و بعداً برای Codex روی `Stop` در همان پروژه یک ترکیب پشتیبانی‌شده است: هر کلاینت رویدادها، matcher، دستور، timeout، پیام وضعیت، مسیرهای رانتایم و مانیفست خودش را نگه می‌دارد، و به‌روزرسان هر کلاینت را با پارامترهای **خودش** ترمیم می‌کند. اضافه‌کردن، حذف یا ترمیمِ یک کلاینت هرگز کلاینت دیگر را بازنویسی نمی‌کند. انتخاب کلاینت هنگام نصب صریحاً ذخیره می‌شود — نه اینکه از روی وجود فایل‌های رانتایم حدس زده شود.

کلاینت‌ها **اجزای مستقل‌اند**. اگر یکی نصب نشود، بقیه نصب می‌شوند و نتیجه‌ی کلی `partial` است نه `failed` — گزارش `failed` به فراخوان می‌گوید دو نصبِ واقعاً موفق را دور بریزد. فقط درخواستی که در آن **هیچ‌چیز** نصب نشده `failed` است.

### Kiro

Kiro به‌ازای هر هوک **یک سند JSON جداگانه** زیر `.kiro\hooks\hookmaker-<hook>-<id>.json` ثبت می‌کند، نه یک فایل تنظیمات مشترک. مالکیت Hook Maker در سطح **entry** است و با نشانگر `[hookmaker:<id>]` اثبات می‌شود؛ بنابراین entryهای بیگانه در همان سند دست‌نخورده منتقل می‌شوند و سندی که در مسیر خودمان باشد ولی متعلق به دیگری از آب دربیاید، بازنویسی نمی‌شود بلکه رد می‌شود. رانتایم در `.kiro\hook-runtime\Hook-Maker\` کپی می‌شود — عمداً **نه** زیر `.kiro\hooks` که Kiro آن را به‌عنوان کانفیگ اسکن می‌کند.

چهار واقعیت Kiro شکل نصب را تعیین می‌کنند و دور زده نمی‌شوند:

- **سطحِ ورودی بین دو سطحِ Kiro فرق دارد و این تفاوت یکدست نمی‌شود.** خودِ Kiro IDE فقط `USER_PROMPT` را مستند کرده، آن هم فقط روی `UserPromptSubmit`؛ ولی Kiro CLI v3 **واقعاً** stdin JSON می‌فرستد — فقط نام و بزرگ‌وکوچکیِ فیلدهایش را منتشر نکرده. پس دستور هر entry به `-Trigger <trigger>` ختم می‌شود و از طریق `kiro-launch.ps1` تولیدشده اجرا می‌شود؛ این launcher رویداد و هویت کلاینت را از راه محیط می‌دهد و بعد هوک را in-process اجرا می‌کند تا stdin و کد خروج واقعی حفظ شوند. هیچ `session_id` ساختگی‌ای تولید نمی‌شود — رفتار وابسته به session به‌جای جفت‌شدن اشتباه، تنزل پیدا می‌کند.
- **ورودی‌ای که ممکن است Kiro ندهد، «تأییدنشده» گزارش می‌شود، نه «قطعاً موجود نیست».** نصب همچنان به‌خاطرش تنزل می‌کند — ثبت هوکی که در سکوت کار نمی‌کند خطای بدتری است — ولی گزارش بیش از آنچه مستندات پشتیبانی می‌کند ادعا نمی‌کند. جمله‌ی «Kiro این را نمی‌دهد» یک واقعیتِ تأییدنشده‌ی CLI v3 را به‌جای واقعیتِ قطعی جا می‌زد.
- **ثبتی که با Kiro تناقض داشته باشد رد می‌شود، نه حدس زده.** اگر trigger ثبت‌شده در `.kiro\hooks` و رویدادی که Kiro گزارش می‌کند به **دو رویداد متفاوت** برسند، هوک به‌جای انتخاب یک شاخه، هشداری روی stderr می‌نویسد و با کد غیرصفر خارج می‌شود. املاهای متفاوتِ **یک** رویداد اول یکدست می‌شوند، پس یک casing نامستندِ CLI v3 هرگز این مسیر را فعال نمی‌کند.
- **Kiro روی `Stop` نمی‌تواند بلاک کند** (روی هیچ‌کدام از دو سطح هدف)، و فقط `SessionStart` و `UserPromptSubmit` خروجی stdout را به کانتکست اضافه می‌کنند. بنابراین هوک‌های گیت‌کننده‌ی Stop به‌طور دائمی `degraded-stop-gate` ثبت می‌کنند، و رویدادی که Kiro برایش trigger ندارد **با نام** گزارش می‌شود — نه در سکوت حذف می‌شود و نه روی trigger دیگری نگاشت می‌شود.

سقف `USER_PROMPT` برابر ۶۴ کیلوبایت **بایتِ UTF-8** است (نه کاراکتر، تا یک prompt غیرASCII در سکوت سه برابرِ حدِ مستندشده اجازه نگیرد)، برش روی مرز کاراکتر انجام می‌شود تا جفتِ surrogate هرگز نصف نشود، و خودِ بریده‌شدن داخل متنِ prompt اعلام می‌شود، نه در سکوت.

Kiro از `SessionStart`، `UserPromptSubmit`، `PreToolUse`، `PostToolUse` و `Stop` پشتیبانی می‌کند؛ هر رویداد دیگری برای Kiro «پشتیبانی‌نشده» گزارش می‌شود ولی نصب برای بقیه‌ی کلاینت‌ها ادامه پیدا می‌کند.

### pre-push بومیِ Git

زنجیره‌ی pre-push بومیِ `Ignore-Rules-Check` بخشی از همان نصب در نظر گرفته می‌شود، شامل کپی‌های همراهِ مدیریت‌شده‌اش (`Secrets-Check` و `Utf8-Encoding-Check`). تغییر در **سورس** یک همراه، یا خراب/گم‌شدن یک همراهِ مدیریت‌شده **روی دیسک**، هوک والد را برای به‌روزرسانی برنامه‌ریزی می‌کند. ترمیم، wrapper را دقیقاً یک بار بازسازی می‌کند، ترتیب `Ignore → Secrets → Utf8 → هوک قبلی` را نگه می‌دارد، زنجیره‌سازیِ fail-closed با `|| exit` و بافر/بازپخشِ یک‌بارخوانِ stdin را حفظ می‌کند، و هوک قبلیِ (غیر Hook-Maker) `pre-push.hookmaker-existing` را **بایت‌به‌بایت دست‌نخورده** باقی می‌گذارد — آن فایل متعلق به کاربر است، پس هرگز هش، بازنویسی یا حذف نمی‌شود.

هر نصب موفق (یک هوک، یک دسته، از-کانفیگ، یک هوک ساخته‌شده/دلخواه، یا موتور سینک، از هر ترکیب کلاینت/دامنه) — از طریق همان مرحله‌ی مشترک داخل `Install-Hook.ps1` — در `state/install-registry.json` در ریشه‌ی پروژه‌ی Hook Maker ثبت می‌شود: **محلی و git-ignored**، هرگز commit نمی‌شود. رکوردها فقط مسیرها، هش‌های محتوا و پارامترهای نصبِ لازم برای تکرار یک به‌روزرسانی را نگه می‌دارند — هرگز مقدار `.env`، مقدار سکرت، محتوای فایل‌ها، یا محتوای prompt/tool-input. نصب دوباره‌ی همان هوک در همان دامنه رکورد موجود را به‌روز می‌کند، نه اینکه یک رکورد تکراری بسازد. نوشتن در رجیستری atomic است و با یک فایل قفلِ کران‌دار محافظت می‌شود، پس دو نصبِ هم‌زمان نمی‌توانند رکوردهای همدیگر را از بین ببرند.

### مرزهای امنِ سورسِ هوک دلخواه

سورس یک هوک به یکی از دو شکل نصب می‌شود، و این تفکیک یک **مرز امنیتی** است نه یک راحتی:

- **بسته (Package)** — اسکریپت در `<ریشه‌ی hooks>/<Name>/<Name>.ps1` است، یعنی پوشه‌ای که *فرزند مستقیمِ* یک ریشه‌ی شناخته‌شده‌ی hooks باشد. محتوای (فیلترشده‌ی) آن پوشه همراهش نصب می‌شود. قالب‌های `.env.example` هرگز منتقل نمی‌شوند، و `.git`، `.ai`، `.claude`، `node_modules`، خروجی بیلد و مواردی از این دست حتی از داخل یک بسته هم کپی نمی‌شوند.
- **مستقل (Standalone)** — هر چیز دیگر، از جمله یک اسکریپت آزاد داخل ریشه‌ی hooks. **فقط همان یک فایل** نصب می‌شود و نام هوک از نام *اسکریپت* گرفته می‌شود.

یک پوشه‌ی والدِ دلخواه هرگز به‌عنوان بسته‌ی هوک در نظر گرفته نمی‌شود، پس اشاره‌دادن `-CustomHook` به اسکریپتی داخل یک پروژه‌ی نامرتبط نمی‌تواند `.git`، `.env`، اعتبارنامه‌ها یا سورس آن پروژه را داخل یک پوشه‌ی رانتایمِ ثبت‌شده در تنظیمات کپی کند. reparse pointها (symlink/junction) به‌جای دنبال‌شدن، رد می‌شوند.

### نصب و به‌روزرسانیِ تراکنشی

جایگزینی رانتایم مرحله‌ای است، نه تخریبی: درخت جدید در یک پوشه‌ی staging کنارِ مقصد ساخته می‌شود و هر artifact برنامه‌ریزی‌شده **پیش از** دست‌زدن به هر چیز زنده با هش راستی‌آزمایی می‌شود، بعد جابه‌جا می‌شود؛ اگر خودِ جابه‌جایی شکست بخورد، رانتایم قبلی برگردانده می‌شود. شکست در هر نقطه‌ی زودتر، نصب موجود را دقیقاً دست‌نخورده باقی می‌گذارد، و پوشه‌های staging رهاشده از یک اجرای نیمه‌کاره در نصب بعدی پاک می‌شوند. فایل‌های تنظیمات هم به همین شکل نوشته می‌شوند — سریال‌سازی در یک فایل موقت کناری، خواندنِ دوباره از دیسک برای اثبات معتبربودن، و بعد جایگزینی atomic — پس یک شکست هرگز نمی‌تواند تنظیماتِ ناقص یا غیرقابل‌خواندن باقی بگذارد.

### مالکیتِ ثبت‌نام

یک handler ثبت‌شده از روی **شکلِ مسیرِ رانتایمِ مدیریت‌شده** به‌عنوان مالِ Hook Maker شناخته می‌شود، و این بررسی روی `command`، `commandWindows` و `command_windows` انجام می‌شود — هرگز از روی نامِ خالیِ فایل. handler خودِ شما که صرفاً به اسکریپتی با نام فایلِ مشابه اشاره می‌کند، در نصب مجدد حفظ می‌شود. دو چیدمان تاریخی هم برای مهاجرت شناسایی می‌شوند (ریشه‌ی قدیمیِ `HookMaker` بدون خط تیره، و شکل تول‌فولدرِ پیش از نصب‌های خوداتکا یعنی `…/hooks/<Name>/<Name>.ps1`)؛ شکل دوم علاوه‌بر آن مشروط به تطابقِ نام هوک با نصبی است که روی آن کار می‌شود.

### اعتبارسنجی ورودی

نصاب پیش از هر تغییری اعتبارسنجی می‌کند: `-ClaudeOnly` و `-CodexOnly` متقابلاً انحصاری‌اند، حداقل یک رویداد معتبر لازم است، نام رویدادها با مجموعه‌ی پشتیبانی‌شده بررسی و تکراری‌ها حذف می‌شوند، و پروژه‌ی مقصد باید از قبل وجود داشته باشد. یک فراخوانی نامعتبر رانتایم، تنظیمات، رجیستری و هوک‌های بومی Git را کاملاً دست‌نخورده باقی می‌گذارد.

### فایل ردیابیِ پایدار

دقیقاً **یک** فایل وضعیتِ پایدار وجود دارد و همان تنها منبع حقیقت است برای اینکه Hook Maker چه چیزی نصب کرده:

```text
<Hook-Maker>\state\install-registry.json
```

متغیر `HOOKMAKER_STATE_DIR` مکانش را override می‌کند، ولی این override برای سوییت‌های تست است (تا هرگز رجیستری واقعی شما را دست نزنند) و برای یک جابه‌جاییِ عمدی و مستند — بخشی از استفاده‌ی عادی نیست. هیچ رجیستری دوم، کش، کاتالوگ، دیتابیس ردیابیِ هر-پروژه، یا فایل منبع‌حقیقتِ پنهانی در هیچ کجا وجود ندارد.

**چه چیزی ذخیره می‌کند:** برای هر نصب، شناسه‌ی رکورد، هویت و نوع هوک، مسیر دقیق اسکریپت سورس و پوشه‌ی سورس، tool root، دامنه و ریشه‌ی پروژه‌ی هدف، profile و مسیر کانفیگ برای نصب‌های موتور، مانیفست فایل‌های مدیریت‌شده (مسیر + هش)، و برای هر کلاینت: مسیر دقیق تنظیمات، runtime root، runtime script، رویدادهای ثبت‌شده، خط‌فرمان‌های تولیدشده، نوع handler، timeout و پیام وضعیت. برای زنجیره‌ی مدیریت‌شده‌ی native Git، مسیر hooks گیت، مسیر wrapper، مراحل مورد انتظار، companionهای متعلق و وضعیت هوک کاربرِ حفظ‌شده را هم نگه می‌دارد.

**چه چیزی هرگز ذخیره نمی‌کند:** مقدار سکرت، محتوای `.env`، متن prompt یا ورودی ابزار، stdin، یا محتوای هیچ فایل کپی‌شده‌ای. فقط مسیرها و هش‌ها.

**منوهای `21` و `22` به آن وابسته‌اند.** کشف فایل‌سیستمی زیر `hooks\` فقط کاتالوگ هوک‌های *در دسترس* برای نصب است — هرگز اثبات اینکه چیزی *نصب شده* نیست. در نتیجه:

- به‌روزرسانی از `sourceScript` **ذخیره‌شده‌ی** هر رکورد تازه می‌شود، نه مسیری که از روی نام هوک بازسازی شده باشد. اگر آن سورس جابه‌جا یا حذف شده باشد، «گم‌شده» گزارش و رد می‌شود — هیچ مسیر دیگری حدس زده نمی‌شود.
- حذف نصب، runtime script و مسیر تنظیمات و دستورِ **دقیقاً ذخیره‌شده‌ی** همان رکورد را هدف می‌گیرد. یک handler فقط وقتی حذف می‌شود که دستور parse‌شده‌اش همان هویت دقیق را اثبات کند؛ handlerای با نام یا basename مشابه که به جای دیگری اشاره کند بیگانه است و باقی می‌ماند.
- **سورس هوک‌ها زیر `hooks\` هرگز توسط هیچ عملیاتی حذف نمی‌شوند.**
- اگر حذف نصب ناقص یا مبهم باشد، رکورد با وضعیت دقیقِ خطا/نیاز-به-ترمیم-دستی **نگه داشته** می‌شود، نه اینکه موفقیتی که رخ نداده گزارش شود.

**تضمین‌های پایداری:** هر تغییر، قفل انحصاریِ آگاه‌به‌کرشِ رجیستری را می‌گیرد، در یک فایل موقتِ همسایه می‌نویسد، قبل از انتشار JSON را دوباره parse می‌کند، و بعد رکورد را می‌خواند تا از ثبت شدنش مطمئن شود. رجیستری‌ای که parse نشود با بایت‌های اصلی دست‌نخورده کنارش قرنطینه می‌شود، نه بازنویسی. رکوردها بین پروسه‌های جدا از هم زنده می‌مانند — این با یک رگرسیون تأیید می‌شود که در یک پروسه نصب می‌کند، در دومی راستی‌آزمایی و به‌روزرسانی، و در سومی حذف نصب.

مثل بقیه‌ی این ابزار، اینجا هم «rollback جبرانی» است نه اتمیک‌بودن در برابر کرش ماشین — بخش «محدودیت‌های شناخته‌شده» را ببین.

### کتابخانه‌ی خصوصیِ رانتایم برای هر هوک

هر هوکِ نصب‌شده نسخه‌ی `_hooklib.ps1` **مخصوص خودش** را داخل پوشه‌ی رانتایم خود دریافت می‌کند و اسکریپت نصب‌شده‌اش به‌صورت قطعی بازنویسی می‌شود تا همان نسخه‌ی خصوصی را dot-source کند. سورس‌های مخزن هرگز تغییر نمی‌کنند؛ محتوای بازنویسی‌شده در پلن هش می‌شود و مثل هر artifact دیگری راستی‌آزمایی می‌شود. این کار انحرافِ نسخه بین هوک‌ها را حذف می‌کند — به‌روزرسانی یک هوک دیگر نمی‌تواند کتابخانه‌ای را که هوکِ نصب‌شده‌ی دیگری بارگذاری می‌کند تغییر دهد. کتابخانه‌ی مشترکِ قدیمی در ریشه‌ی رانتایم فقط زمانی حذف می‌شود که هر هوکِ زیر آن ریشه نسخه‌ی خصوصی خود را داشته باشد، پس هوک‌هایی که با نسخه‌های قدیمی نصب شده‌اند تا زمان به‌روزرسانی کار می‌کنند.

### اعتبارسنجی رجیستری و ایزوله‌سازیِ هر رکورد

هر رکورد پیش از خوانده‌شدنِ هر فیلدش اعتبارسنجی می‌شود: فیلدهای الزامی و نوعشان، scope، نوع هوک، profile/config موتور، زیررکوردهای هر کلاینت (مسیر رانتایم، مسیر تنظیمات، رویدادهای غیرخالی) و شکلِ ورودی‌های manifest. نسخه‌ی schema **جدیدتر** از آنچه این بیلد پشتیبانی می‌کند صریحاً رد می‌شود، نه اینکه معتبر فرض شود؛ و نسخه‌ی قدیمی‌تر به‌عنوان نیازمندِ مهاجرت گزارش می‌شود.

رکوردی که اعتبارسنجی را رد کند — یا ارزیابی‌اش به هر دلیل دیگری خطا بدهد — به یک skip ایزوله و دقیقاً گزارش‌شده تبدیل می‌شود. هرگز کلِ اجرا را متوقف نمی‌کند، بقیه‌ی رکوردها همچنان ارزیابی می‌شوند، و هیچ چیزی از رکوردِ خراب تغییر داده یا حدس زده نمی‌شود؛ برای تعمیر دستی باقی می‌ماند.

### تعمیر در سطحِ مؤلفه

بررسی یکپارچگی به‌جای توقف در اولین مشکل، نتیجه‌ای به‌ازای هر مؤلفه گزارش می‌کند — source، Claude، Codex و native Git. سپس به‌روزرسان **فقط** مؤلفه‌های آسیب‌دیده را دوباره نصب می‌کند. تعمیرِ یک کلاینتِ سالم فایل تنظیماتش را بازنویسی می‌کرد، یک بکاپِ زمان‌دارِ دیگر اضافه می‌کرد و زمانِ فایل‌های رانتایمش را جابه‌جا می‌کرد؛ بنابراین کاملاً دست‌نخورده باقی می‌ماند و همین هم گزارش می‌شود.

تغییرِ **سورس** یک وابستگیِ مشترک است: همه‌ی کلاینت‌ها طبق تعریف کهنه می‌شوند و با هم تازه‌سازی می‌شوند. هوکِ pre-push متعلق به کاربر اگر گم شده باشد به‌عنوان `manual repair required` گزارش می‌شود و هرگز با بازسازی «تعمیر» نمی‌شود.

### راستی‌آزماییِ فیلدهای ثبت‌نام

هر فیلدی که نصاب مالکِ آن است به‌صورت **مستقل** و به‌ازای هر کلاینت و رویداد راستی‌آزمایی می‌شود: نوع handler، `command`، `commandWindows`، timeout، statusMessage، matcher، تعدادِ دقیقِ تکرار، و نبودِ ثبت‌نامِ کهنه روی رویدادهای دیگر. یک فرمانِ portable سالم دیگر نمی‌تواند یک `commandWindows` خراب را پنهان کند — handlerهای Codex هر دو شکل را دارند و هرکدام جداگانه بررسی می‌شود.

فیلدهایی که Hook Maker مالکشان نیست دست‌نخورده می‌مانند، و رکوردی که پیش از ردیابیِ یک فیلد نوشته شده صرفاً انتظاری برای آن ندارد، نه اینکه «منحرف» گزارش شود.

### خروجی‌های ساخت‌یافته

`Install-Hook.ps1 -ResultPath <file>` یک سندِ نسخه‌دار و ماشین‌خوان می‌نویسد که نتیجه‌ی هر مؤلفه را توصیف می‌کند (اعتبارسنجی، Claude، Codex، native Git، رجیستری). فراخوانندگان برنامه‌ای همان را می‌خوانند، نه متنِ کنسول را و نه فرضِ «خطایی رخ نداد پس موفق بود».

حالت‌هایی که اهمیت دارند تفکیک می‌شوند: `ok`، `failed`، `skipped` (مربوط به این فراخوانی نیست) و `trackingFailed` — رانتایم و تنظیمات اعمال شده‌اند ولی نوشتنِ رجیستری انجام نشده، که به‌عنوان **partial** گزارش می‌شود، هرگز به‌عنوان موفقیت. به‌روزرسان این سند را مصرف می‌کند **و** مستقلاً رکورد را دوباره می‌خواند و یکپارچگی را دوباره راستی‌آزمایی می‌کند، پس چیزی به‌عنوان به‌روزشده گزارش نمی‌شود مگر واقعاً current باشد.

خودِ ماندگاریِ رجیستری هم راستی‌آزمایی می‌شود نه فرض: پس از نوشتن، رجیستری دوباره خوانده و وجودِ دقیقِ همان رکورد تأیید می‌شود. (پیش‌تر اگر یک پوشه در مسیرِ رجیستری قرار می‌گرفت، نوشتنِ atomic فایل را *داخلِ* آن می‌برد و موفقیت گزارش می‌کرد.)

### تاریخچه‌ی هر مؤلفه

هر رکورد یک تاریخچه‌ی **کران‌دار** (۱۰ تلاش آخر) نگه می‌دارد که هر ورودی‌اش نتیجه‌ی هر مؤلفه را برای آن تلاش دارد، نه یک حکمِ تخت — بنابراین یک شکستِ جزئی بعداً هم قابل‌مشاهده می‌ماند و با یک `ok` بعدی پاک نمی‌شود. ورودی‌ها فقط زمان، نام مؤلفه، وضعیت و کد دلیل را نگه می‌دارند: هرگز محتوای فایل، مقادیر `.env`، متنِ prompt یا خروجی خام.

### محدودیت‌های شناخته‌شده

- کشف/حذفِ چیدمان‌های قدیمی فقط از چیدمان‌های تاریخیِ فهرست‌شده در بخش «مالکیتِ ثبت‌نام» پشتیبانی می‌کند؛ شکل‌های تاریخیِ دیگر گزارش می‌شوند، نه بازنویسی.
- پوشه‌های رانتایم و یکپارچه‌سازی native Git قفل اختصاصیِ بین‌فرایندی ندارند؛ رجیستری و هر فایل تنظیمات دارند.
- جایگزینی رانتایم مرحله‌ای، هش‌راستی‌آزمایی‌شده و سپس جابه‌جا می‌شود و در صورت شکستِ جابه‌جایی رانتایم قبلی برگردانده می‌شود. این «rollback جبرانی» است، نه اتمیک‌بودن در برابر کرش: ماشین یا فرایندی که وسط جابه‌جایی خاموش شود ممکن است هنوز به یک نصب مجدد نیاز داشته باشد. همین موضوع درباره‌ی حذف یک هوکِ کشف‌شده هم صادق است.
- اسکن وضعیت (`22`) فقط چیزی را گزارش می‌کند که واقعاً توانسته به آن برسد. دایرکتوری‌هایی که خوانده نشدند و نقاط reparse که عمداً دنبال نشدند فهرست می‌شوند و اجرا **partial** گزارش می‌گردد — ادعا نمی‌شود که هر دایرکتوری ناخوانا، سیستمی یا reparse اسکن شده است.
- ثبت‌نامی که دستورش به یک هدف مشخص پارس نمی‌شود همچنان به‌عنوان هوک نصب‌شده گزارش می‌شود، ولی خودکار قابل حذف نیست — هدفِ اثبات‌شده‌ای برای عمل‌کردن روی آن وجود ندارد.

### اگر رجیستری خراب شود

رجیستری‌ای که خوانده نمی‌شود، JSON معتبر نیست، از نظر ساختاری نامعتبر است، یا با schema جدیدتری نوشته شده، **هرگز** بی‌صدا خالی فرض و بازنویسی نمی‌شود. نصب بعدی بایت‌های دقیقش را زیر نام `state/install-registry.corrupt-<timestamp UTC>-<هش کوتاه>.json` حفظ می‌کند، با ذکر همان مسیر هشدار می‌دهد، و تنها بعد از آن یک رجیستری تازه می‌سازد. اگر قرنطینه ممکن نباشد، فایل کاملاً دست‌نخورده می‌ماند و نصب گزارش می‌دهد که **ردیابی شکست خورده** — ممکن است خودِ هوک درست نصب شده باشد، ولی هرگز ادعا نمی‌شود که ردیابی شده است. به‌روزرسان هم به‌جای گزارشِ گمراه‌کننده‌ی «به‌روز است»، از فهرست‌کردن یا راستی‌آزمایی روی یک رجیستری خراب خودداری می‌کند.

هوکی که با نسخه‌ی **قدیمی‌تر** Hook Maker نصب شده (قبل از وجود این رجیستری) به‌محض اجرای گزینه‌ی `4` خودکار شناسایی می‌شود، برای پروژه‌ی فعلی، دامنه‌ی سراسری، و هر پروژه‌ی دیگری که از قبل در profileهای کانفیگ سینک تو ثبت شده — تنها دامنه‌هایی که یک مسیر پایدار برایشان شناخته‌شده است. یک نصبِ مدیریت‌شده‌ی Hook Maker در یک پروژه‌ی دیگر و ناشناخته این‌طور قابل‌کشف نیست؛ یک‌بار (با هر روشی) آنجا دوباره نصبش کن تا از این پس وارد رجیستری شود.

## فرمت hook در Claude و Codex

- **Claude Code:** زیر کلید `hooks`؛ `timeout` بر حسب ثانیه است و matcher رویداد SessionStart مقادیر `startup|resume|clear|compact` را می‌پذیرد.
- **Codex CLI:** رسمی از hooks پشتیبانی می‌کند، فایل `hooks.json` با همان ساختار `{"hooks": {...}}`. فیلد `commandWindows` مخصوص ویندوز و رسمی است. بعد از نصب حتماً `/hooks` را بزن و hook را trust کن.
- منبعی که پوشه `.ai` خالی دارد، بی‌صدا baseline می‌شود و بسته بازبینی خالی نمی‌سازد.

## ساخت هوک دلخواه

سینک `.ai` فقط یکی از هوک‌هاست. هر هوک یک اسکریپت در پوشه‌ی `hooks\` است که یک JSON از stdin می‌خواند و در صورت نیاز یک JSON روی stdout چاپ می‌کند. نمونه‌ی حداقلی (`hooks\MyHook.ps1`):

```powershell
$e = [Console]::In.ReadToEnd() | ConvertFrom-Json
# $e.hook_event_name و $e.cwd و $e.session_id و فیلدهای رویداد (مثل $e.prompt) در دسترس‌اند.
exit 0                       # اگر حرفی نداری
# یا برای تزریق context:
@{ hookSpecificOutput = @{ hookEventName = $e.hook_event_name; additionalContext = 'متن' } } |
    ConvertTo-Json -Depth 5 -Compress
```

فایل را در `hooks\` بگذار و از منوی لانچر گزینه ۱ ← «نصب هوک موجود» را بزن — خودش در پروژه‌های هدف نصبش می‌کند. اگر کانفیگ خواست، مثل `sync-hooks.json` یک JSON جدا کنارش بگذار.

### هوک آماده: Git-Sync-Check (چک سینک با گیت‌هاب)

`hooks\Git-Sync-Check.ps1` از قبل آماده است: روی رویداد SessionStart نصبش کن (منو گزینه ۲ → نصب هوک موجود). هر بار که پروژه‌ای را باز کنی که با ریموتش (گیت‌هاب) سینک نیست، قبل از شروع کار به عامل گفته می‌شود:

- تغییرات commit نشده در working tree
- کامیت‌های push نشده (AHEAD)
- کامیت‌های pull نشده (BEHIND)
- شاخه‌ای که هرگز push نشده (بدون upstream)

پروژه‌ی سینک‌شده یا غیر-گیت → کاملاً ساکت. اگر اینترنت نباشد، با آخرین وضعیت شناخته‌شده‌ی ریموت مقایسه می‌کند و همین را هم اعلام می‌کند.

## مفاهیم اصلی

### ۱. Profile

هر profile یک hook منطقی مستقل است. می‌تواند قوانین، رویدادها و چند route مخصوص خودش را داشته باشد.

### ۲. Route

هر route یک جهت انتقال اطلاعات را مشخص می‌کند: `source -> destination`

برای ارتباط دوطرفه باید دو route تعریف شود. این کار عمداً صریح است تا هیچ پروژه‌ای به‌اشتباه منبع یا مقصد فرض نشود.

### ۳. گروه همگام‌سازی (full mesh)

ویزارد برای N پروژه، N×(N-1) route می‌سازد؛ یعنی هر پروژه مقصدِ همه‌ی پروژه‌های دیگر است و حافظه‌ی همه همیشه سینک می‌ماند.

**گروه‌هایی که هم‌پوشانی دارند خودکار ادغام می‌شوند.** اگر گروهی که می‌سازی حتی یک پروژه‌ی مشترک با یک گروه موجود داشته باشد، این دو در واقع یک mesh‌اند — تو آن‌ها را به هم وصل کرده‌ای. ویزارد بستارِ گذرا (transitive closure) را حساب می‌کند و **یک** profile با mesh کامل روی اجتماعِ همه می‌نویسد: `A,B,C` را سینک کن، بعد `D` را با `C` سینک کن، آن‌وقت `D` با `A`، `B` **و** `C` mesh می‌شود، نه فقط `C`. profile ادغام‌شده id گروه بزرگ‌تر را دوباره استفاده می‌کند، پس هوک‌های از قبل نصب‌شده‌ی آن گروه بدون نصب مجدد کار می‌کنند و mesh گسترده را از کانفیگ زنده می‌گیرند — فقط پروژه‌ی جدید (و هر عضو گروه کوچک‌ترِ جذب‌شده که id قدیمی‌اش حذف می‌شود) نصبِ موتور می‌گیرد. routeی که صریحاً غیرفعال کرده بودی بعد از ادغام غیرفعال می‌ماند و هرگز بی‌صدا دوباره فعال نمی‌شود.

## ویرایش sync-hooks.json

ساختار اصلی:

```json
{
  "version": 2,
  "defaults": { },
  "profiles": [ ]
}
```

برای ساخت profile دستی، profile نمونه‌ی غیرفعال داخل `sync-hooks.json` را کپی کن و موارد زیر را عوض کن (البته روش ساده‌تر همان ساخت گروه سینک از ویزارد است):

- `id`: شناسه یکتا و ثابت، فقط با حروف انگلیسی، عدد، خط تیره یا زیرخط
- `name`: نام نمایشی
- `enabled`: فعال یا غیرفعال
- `events`: رویدادهای اجرای profile
- `initialSyncMode`: رفتار اجرای اول
- `reviewInstructions`: قوانین اختصاصی بررسی
- `routes`: مسیرهای انتقال

نمونه‌ی route یک‌طرفه:

```json
{
  "id": "source-to-destination",
  "enabled": true,
  "source": {
    "name": "Source Project",
    "root": "D:\\Projects\\Source Project",
    "directory": ".ai",
    "aliases": []
  },
  "destination": {
    "name": "Destination Project",
    "root": "D:\\Projects\\Destination Project",
    "directory": ".ai",
    "aliases": []
  }
}
```

برای دوطرفه‌شدن، route دوم را با source و destination معکوس اضافه کن.

### چند منبع برای یک مقصد

سه route مستقل بساز: `A -> D` و `B -> D` و `C -> D`. وقتی عامل داخل Project D شروع به کار کند، هر سه route بررسی می‌شوند. فقط منبعی که نسبت به آخرین acknowledgement تغییر واقعی داشته باشد وارد context می‌شود.

### aliases

اگر یک پروژه از چند مسیر باز می‌شود، مسیرهای جایگزین را در aliases بنویس (متغیرهای محیطی ویندوز پشتیبانی می‌شوند):

```json
"aliases": [
  "D:\\Worktrees\\Project A",
  "%USERPROFILE%\\Projects\\Project A"
]
```

### initialSyncMode

- `review`: در اولین اجرا تمام فایل‌های مجاز منبع به‌عنوان بسته اولیه برای بررسی ارائه می‌شوند.
- `baseline`: در اولین اجرا فقط fingerprint ثبت می‌شود و چیزی به مدل فرستاده نمی‌شود. فقط تغییرات بعدی بررسی می‌شوند.

## قانون عدم اتلاف وقت

هر route وضعیت مستقل دارد. در هر اجرا ابتدا fingerprint سریع از مسیر نسبی، حجم و زمان تغییر فایل‌ها ساخته می‌شود:

- اگر fingerprint با آخرین وضعیت پردازش‌شده یکسان باشد، اسکریپت بدون خروجی تمام می‌شود.
- اگر فقط timestamp تغییر کرده باشد، SHA-256 بررسی می‌شود و در صورت یکسان‌بودن محتوا چیزی به مدل ارسال نمی‌شود.
- هش کامل فقط وقتی محاسبه می‌شود که fingerprint سریع تغییر کرده باشد.
- یک pending review در همان session فقط یک‌بار نمایش داده می‌شود.
- پوشه `.cross-project-sync` از بررسی حذف است و حلقه ایجاد نمی‌کند.

## گزینه‌های قابل override

این گزینه‌ها را می‌توان در defaults، profile یا route قرار داد. مقدار route بالاترین اولویت را دارد:

`events`، `initialSyncMode`، `maxFileBytes`، `includeExtensions`، `excludePatterns`، `reviewInstructions`

## نصب دستی (بدون ویزارد)

نصب داخل یک پروژه (همان کاری که ویزارد می‌کند):

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Install-Hook.ps1" -Profile "<profile-id>" -TargetProject "<مسیر پروژه>"
```

نصب سراسری همه profileها با یک hook:

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Install-Hook.ps1"
```

فقط Claude یا فقط Codex: سوییچ `-ClaudeOnly` یا `-CodexOnly` را اضافه کن.

نصب هوک دلخواه بدون ویزارد:

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Install-Hook.ps1" -CustomHook ".\hooks\MyHook.ps1" -Events SessionStart,UserPromptSubmit -TargetProject "<مسیر پروژه>"
```

اعتبارسنجی کانفیگ:

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Validate-Config.ps1"
```

تست موتور (۱۸ سنجش، زیر pwsh و PowerShell 5.1):

```powershell
pwsh -NoLogo -NoProfile -File ".\scripts\Test-Engine.ps1"
```

## نکته‌ها

- بعد از تغییر id یک profile یا route، وضعیت قبلی دیگر به آن وصل نیست و route به‌عنوان یک route جدید شناخته می‌شود. بنابراین idها را پس از شروع استفاده ثابت نگه دار.
- محل وضعیت و بسته‌های موقت در `destination.directory` ساخته می‌شود: `‎.ai\.cross-project-sync\state` و `‎.ai\.cross-project-sync\inbox`. این مسیر باید در ignore rules قرار بگیرد و نباید commit شود.
- اگر می‌خواهی هر profile در `/hooks` به‌صورت command جدا دیده شود، `Install-Hook.ps1` را یک‌بار برای هر profile با پارامتر `-Profile` اجرا کن.
